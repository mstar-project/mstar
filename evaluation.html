Evaluation and Benchmarks#

python -m benchmark.eval measures a served model end to end: speed (latency, throughput, streaming stalls) and quality (WER, speaker similarity, MOS, duplex turn timing) from the same requests, repeated, with every number written to one results file that also records the commit, GPU, versions and settings that produced it. The same client can drive M*, vLLM-Omni and SGLang-Omni, so comparisons use one metric definition.

It lives in benchmark/eval/ (not shipped in the wheel). Install the optional dependencies with the eval extra, ideally in a separate client environment:

pip install -e ".[eval]"

Quick start#

Build a dataset once, then run a suite against a server the runner launches itself:

python -m benchmark.eval data librispeech --out ~/eval-data/ls_clean --n 200

python -m benchmark.eval run tts --serve kokoro --voice af_heart \
    --data benchmark/assets/t2s.txt --concurrency 1,4,16 --repeats 3 --out results/kokoro

python -m benchmark.eval report results/kokoro --md kokoro.md \
    --chart kokoro.png --chart-metrics ttfa_ms_p50,audio_s_per_s,wer

--serve MODEL runs mstar serve MODEL with its own port, ZMQ socket prefix and upload directory, waits for GET /health, logs to <out>/server-<label>.log and stops the whole process group afterwards. --url measures a server that is already running, and --serve-cmd "<command with {port}>" launches anything else (for example another engine for a side-by-side run).

How a run is measured#

A run is one suite at one or more load points. For each point the runner sends --warmup untimed requests at the measured concurrency, then --repeats passes over the items, scoring each pass on its own. A results file holds one point.

  • Closed loop (--mode closed, default): --concurrency requests in flight at all times. --concurrency 1,4,16 sweeps; each level writes its own file.

  • Open loop (--mode open --rate 1,2,4): Poisson arrivals at each rate, seeded (--arrival-seed) so every system sees the same schedule. --concurrency N caps in-flight requests; latency is measured from the scheduled arrival, so time spent waiting for a slot counts (slot_wait_s). Each request also records how late the client was against the schedule (arrival_lateness_s); a large arrival_lateness_s_p99 means the client, not the server, set the pace, and the point should not be used.

  • Repeats: every metric is one number per repeat (a p50 over that repeat’s requests, a corpus WER, …); the summary is mean +- sample std over repeats. Three repeats is the default and what a PR table should show.

Suites#

tts

Streaming /v1/audio/speech. Per request: time to first audio (first PCM byte after the WAV header), end-to-end latency, audio seconds, RTF, and the playback stalls a real-time player fed by the stream would hit (--stall-prebuffer-ms, --stall-min-ms). Per repeat, optionally: round-trip WER (--asr-judge, Whisper large-v3 by default; CER for zh/ja/ko/th), speaker similarity to each item’s reference clip (--clone sends it as ref_audio; --sim-judge) and UTMOS (--mos). --engine vllm-omni|sglang-omni reads their raw PCM streams.

asr

/v1/audio/transcriptions. Corpus WER (CER for character languages) against the manifest, latency percentiles, RTFx (audio seconds per wall second), and with --stream the time to the first transcript delta. A failed request scores as an empty transcript, so errors never lower the WER.

duplex

Streamed /generate for frame-synchronous speech-to-speech models (nemotron_duplex). The output is time-aligned with the input, so latencies are measured in interaction time from a replay: response latency after the user stops, whether the agent took the turn, and on barge-in clips the stop latency and whether it yielded; plus wall time per frame and whether each session kept up with real time. data duplex-synth builds turn-taking and barge-in clips from any 16 kHz ASR manifest.

Datasets#

A dataset is a JSONL manifest, one item per line, with paths relative to the manifest (a .txt file of sentences also works for tts):

{"id": "1089-134686-0000", "text": "...", "audio_path": "audio/1089-134686-0000.wav", "lang": "en"}

ref_audio and ref_text add a voice-clone prompt; extra carries suite fields (duplex category, speech_end_s, interrupt_s). An id names the item’s saved audio, so it must be a plain name (letters, digits, ., _, -). Builders:

data kind

Downloads go to the Hugging Face cache, so set HF_HOME to a large disk on GPU hosts and reuse it across runs.

Quality judges#

Model-based scores depend on the judge, so every results file names it, and tables should only compare runs scored by the same judge and normalizer.

  • WER normalizers (--normalizer): whisper (default; Whisper’s convention, per item: its English normalizer for English items and items with no language, its basic normalizer for every other language), whisper_en (English only; a run whose items are in another language is refused before it starts), seedtts (the Seed-TTS-eval recipe: punctuation removed except the apostrophe), whisper_basic, basic. Both the corpus rate (wer) and the per-utterance mean (wer_utt_mean, what Seed-TTS-eval publishes) are kept.

  • Speaker similarity uses microsoft/wavlm-base-plus-sv x-vectors; Seed-TTS-eval’s published SIM uses a WavLM-large ECAPA checkpoint, so absolute values differ.

  • UTMOS is UTMOS22 strong from tarepan/SpeechMOS on torch.hub.

Judges run between repeats, after the load has finished, so they never compete with measured requests; --judge-device moves them to another GPU or the CPU.

Results and reports#

Each results file (schema: "mstar-eval/1") has config (everything that decides the numbers: data slice, load, repeats, request fields, judges), meta (git commit and dirty flag, GPUs, driver, Python/torch/CUDA versions, MSTAR_* environment, the server’s /v1/models identity and launch settings, the CLI command and flag names), repeats (per-repeat metrics and per-request rows) and summary (mean, std, min, max, n per metric).

Results files are meant to be shared, so they never carry addresses, secrets or home paths: values under secret-looking keys are dropped, host-like keys keep only loopback values, a --serve-cmd is recorded as a fingerprint and --serve-arg values as flag names plus a fingerprint, and raw command lines are not recorded. A failed request keeps only an error category (HTTP 503, an exception type); the server’s message and the exception text go to <out>/errors-<suite>-<label>-<load>.log next to the server log.

report turns any set of files into one markdown table per suite, headed by a provenance line, plus optional PNG charts of metrics against concurrency or rate. --metrics picks the columns. For a PR, paste the table and link the chart.

rescore recomputes WER/CER from the transcripts a tts or asr results file already holds, with another normalizer, and records that it did; transcribing is the expensive part, so runs scored differently can be compared without a GPU. It refuses a file whose transcripts were redacted when written (they held an address or a home path), since it would score the redaction:

python -m benchmark.eval rescore results/tts --data eval-data/fleurs_en/manifest.jsonl \
    --normalizer seedtts --out results/tts_seedtts

Adding a suite#

Subclass benchmark.eval.suites.base.Suite: declare its CLI flags in add_args, send one request in request (return a row dict; keys starting with _ stay in memory, for example decoded audio for scoring), compute one number per metric in score, list it in benchmark/eval/suites/__init__.py, and add its default table columns to benchmark/eval/report.py. test/modular/test_eval_framework.py runs every suite against a stdlib fake server on CPU; add a case there.
