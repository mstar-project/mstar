A submodule turns routed tensors into output tensors. Keep host bookkeeping in `prepare_inputs`, tensor computation in `forward`, and decisions that read device results in `check_stop`. The [authoring path](/adding_models) describes how to reach a first working request; this page records the hooks and their execution constraints.

## Compute hooks {#step-4-implement-the-submodules}

Each node name maps to a [`mstar.model.submodule_base.NodeSubmodule`](https://github.com/mstar-project/mstar/blob/main/mstar/model/submodule_base.py), which is a `torch.nn.Module`. Autoregressive nodes use the `ARNodeSubmodule` subclass. The methods are:

### `prepare_inputs` {#prepare-inputs}

`prepare_inputs(self, graph_walk, fwd_info, inputs, **kwargs) -> NodeInputs`

Convert the routed `NameToTensorList` into a typed `NodeInputs`, or into an `ARNodeInputs` with `input_ids` or `input_embeds`. This method runs once per request. Do only cheap host-side work here: shape and length bookkeeping, building position metadata, slicing token id lists. Do not launch GPU compute here. GPU compute belongs in `forward`. The engine may call `prepare_inputs` on a different thread from the GPU thread, and much earlier than execution.

Always set `input_seq_len`. This field is on the base `NodeInputs` class and has two important uses. The engine sums it across the batch to select a accelerator-graph capture bucket and to compute padding sizes, and `declare_step` normally computes its spans from it. Leave it at 0 only when the submodule's inputs are not sequence-shaped. If `declare_step` needs a value that `forward` does not use, put that value in `resource_step_info`.

### `get_input_sequence_len` {#get-input-sequence-len}

`get_input_sequence_len(self, graph_walk, fwd_info, inputs, **kwargs) -> InputSeqLenInfo | None`

Return the length of the row's whole input, before any cached prefix is cut -- the engine subtracts what the prefix cache already holds. Return `None` for a walk that declares no length, or when the inputs it would measure are absent. Read off input shapes alone: this runs before `prepare_inputs`.

### `speculative_input_seq_len` {#speculative-input-seq-len}

`speculative_input_seq_len(self, graph_walk, fwd_info, prev_seq_len) -> int | None`

Estimate the length of a row continuing from the step in flight, before that step's outputs reach it; `prev_seq_len` is its length in that step, or -1 if it ran on another node. The default repeats `prev_seq_len`. Only an estimate: it sizes the token budget left for the rows a speculation merges in beside it. A walk with a fixed length (one token a decode step) should return it.

### `declare_step` {#declare-step}

`declare_step(self, graph_walk, request_ids, inputs, slot_lease=None, piecewise_leases=None, per_request_info=None, **kwargs) -> SubmoduleStep | None`

Declare what this batch's step does to the node's resources. See [Declare resource effects for a step](/model_submodules#step-4a-declare-the-step).

### `preprocess` {#preprocess}

`preprocess(self, graph_walk, engine_inputs, inputs) -> dict`

Collate a list of `NodeInputs` into the keyword arguments that `forward` expects. The default implementation handles batch size 1. Override it to support batching. `ARNodeSubmodule` declares this method abstract, because autoregressive submodules normally support continuous batching. You can still disable batching for one node, or for specific graph walks. See [Batching and graph capture](/model_capture#step-5).

### `forward` {#forward}

`forward(self, graph_walk, engine_inputs, **kwargs) -> NameToTensorList`

The tensor-to-tensor computation. The keys of the returned dict are the edge names that the graph routes downstream. Read resources from `engine_inputs.resources[key]`. See [Reaching your resources](/model_submodules#reaching-your-resources).

### Compilation

The engine applies `torch.compile` to both `forward` and `forward_batched`, for every submodule. It also captures accelerator graphs for them when you declare capture configs (see [Batching and graph capture](/model_capture#step-5)). To disable compilation for a submodule, set the class attribute `disable_torch_compile = True`. An encoder whose output feeds a prefix cache layout walk compiles with dynamic shapes instead. One that marks every dimension that varies with `torch._dynamo.mark_dynamic` in `prepare_inputs` sets `marks_dynamic_dims = True` and compiles as any other submodule. The engine raises the recompile limit around a node's compiled calls, past `MSTAR_RECOMPILE_LIMIT`, to hold an entry per bucket its compiled captures take (each batch size and token count); a submodule whose frames keep several entries per bucket (GLM-5.2's decoder layers are traced once per layer kind) declares how many as `compiled_entries_per_shape`. Keep the compiled paths compile-friendly. If a helper must not be traced, because it uses data-dependent Python control flow or forces a host synchronization, exclude it explicitly with `@torch.compiler.disable`.

A submodule that disables the whole-forward compile but wants parts of it compiled returns them from `compile_regions()`: attribute paths (a module, or a method) mapped to example arguments to warm each with at start-up. The engine compiles them, with dynamic shapes and before capture, on an accelerator only; prefer it to calling `torch.compile` in model code. Its options are fixed (dynamic shapes, torch.compile's default mode), so a part that needs static shapes, a mode or `fullgraph` still compiles in model code. Qwen3.5's vision encoder and Omnilingual ASR are examples.

### Parameter dtype and autocast

Some submodules must run in their own parameter dtype. One example is an fp32 vocoder that is numerically sensitive. Such a submodule sets `disable_autocast = True`. The engine then does not cast its parameters to the autocast dtype, does not wrap its forward in autocast, and explicitly disables any enclosing autocast. These two class attributes replace the removed `get_stateless_flavor` method.

### Float32 precision

The engine runs float32 matmuls as TF32 in every process (`torch.set_float32_matmul_precision("high")`). A node that needs full fp32, for example a flow solve that amplifies TF32 rounding, sets `float32_matmul_precision = "highest"`, and `cudnn_allow_tf32 = False` for cuDNN convolutions and RNNs. The engine applies these around that node's forward, its compile and its CUDA-graph capture, and restores the default afterwards, so other nodes keep TF32. `None` (the default) keeps the process setting. Don't flip `torch.backends` flags in model code: they are process-wide, and a CUDA graph keeps the precision it was captured with. The setting covers `forward` and `forward_batched` only, not `preprocess` or `postprocess`. It can also be set per instance in `__init__`, for example only when the model loads in fp32.

### cuDNN capture sizing

A node whose captured convolutions are faster with cuDNN's timed algorithm choice sets `capture_cudnn_benchmark = True`: the engine turns `torch.backends.cudnn.benchmark` on around that node's capture sizing only, so each captured shape is searched once, and eager steps keep the heuristic pick (Kokoro is an example). The search tries workspaces as large as the GPU has free, so on a deployment that sets `gpu_memory_fraction` the engine holds the allocator to that share while it sizes the node's captures, and the boot fails if the node's largest eager step does not fit in it beside what the worker already holds.

### `postprocess` {#postprocess}

`postprocess(...)`

Metadata-only fixups that run on the GPU thread. This method must not read tensor values. Do not call `.item()`, `.cpu()` or `.tolist()` here. This is a performance requirement, not a correctness requirement. Reading a value forces a host synchronization, which stalls the GPU thread and loses the worker's asynchronous scheduling overlap. Use this method only to rename outputs for routing. Put decisions that depend on tensor values in `check_stop`.

### `check_stop` {#check-stop}

`check_stop(...) -> set[str] | StopCheck`

Runs off the GPU thread, and may read tensor values. Return the names of the `Loop` objects to stop, for example after seeing the EOS token. This is how a decode loop terminates. An AR submodule whose loop ends on a stop token sets `self.token_stop = TokenStop(...)` in `__init__` instead of writing one; that also gives it `check_stop_batched`, which checks a whole step off one host copy of its tokens. Qwen3.5's `LLMSubmodule` is an example. The token budget is the loop's cap from `get_loop_caps`, not a stop check. A decode walk that feeds each row its last sampled token can keep that token on the device instead of routing it, with a `DeviceLoopback` (see [Device loop-back](/model_submodules#device-loop-back)).

#### Stop during prefill

A prefill samples the first token before its decode loop exists, so a stop there is returned as `END_PARTITION` (from `mstar.model.submodule_base`) instead: the worker reports the partition done with that pass, and the conductor ends it rather than start decode. Return it only from a row outside any loop; from inside one the request fails. `TokenStop` does this for the walks in its `prefill_walks`, whose token counts toward the budget, so `get_loop_caps` gives the loop `max(1, max_output_tokens - 1)`. Its `last_prefill_flag` names the `step_metadata` flag of the pass whose token is the reply's first, so a stop id sampled on an earlier pass ends nothing. `SampledTokenDecoder` names `FINAL_PREFILL`, which the model's walk plan sets on that step.

#### When not to end the partition

It suits a partition with nothing left to run once generation stops: `END_PARTITION` ends the partition whatever its plan has left, so a model that runs another walk after its loop (an `align` walk, or image generation after thinking) or publishes final-only state at the loop's stop must not return it there. Keep `check_stop_batched`, if you write one, in agreement.

#### Withhold streamed outputs

To also keep some of this step's outputs from being routed, return `StopCheck(stops, withheld=(names...))`, for example a frame streamed alongside the EOS token: its consumer then never receives it, instead of finding and dropping it with a device read. `check_stop_batched` returns a `BatchedStopCheck` for the same. The Qwen3-Omni Talker and Fish S2 Pro's AR keep their EOS frame out of the codec stream this way; a `TokenStop` names such outputs in `withhold`, left unrouted on a row whose token is a stop id (the Qwen3-TTS Talker).

#### Withholding restrictions

Only an output that leaves by a streaming edge can be withheld (any other consumer would wait for an item that never comes), and not one that a node this worker speculates into reads, nor the loop-back signal. Startup refuses a `TokenStop.withhold` that breaks this; a `StopCheck` from `check_stop` is not checked.

### `on_request_added` {#on-request-added}

`on_request_added(self, request_id, request_info)`

Called on the worker's main thread when the request reaches the worker, before any of its steps, with the request's first `CurrentForwardPassInfo`. For host work worth starting early on a thread of the submodule's own; it must not touch the device. The DiT scaffold draws a request's seeded noise here (`PREFETCH_SEEDS`).

### `get_stop_policies` {#get-stop-policies}

`get_stop_policies(self, graph_walk) -> dict[str, StopPolicy] | None`

Declare what `check_stop` amounts to on a walk, per loop it can stop, when it is only the common checks; the graph runtime then runs them over the step's token column without calling `check_stop`. That takes the batched output carrying the policies' `token_signal` as a stop buffer (`BatchedModelOutput(check_stop_buffers={...})`, as Qwen3.5 and Orpheus return); a step without one, or one that mixes walks, still calls `check_stop`. `StopPolicy(StopKind.AR, token_signal=..., eos_tokens=..., sampler=...)` stops its loop on an EOS token (unless the `sampler` resource's request config sets `ignore_eos`) or when the loop's iteration count plus one reaches `max_iters` (`info.max_tokens` unless given). `StopKind.ITER` checks only the count, and `StopKind.EOS` only the token, for a loop whose cap is its budget. `ignores_eos=` replaces `sampler` for a node with no such resource: a callable on the forward-pass info, which it reads for every partition of the request on the worker.

The limits are computed from the request's forward-pass info whenever the worker receives it, not per step. Return `{}` for a walk on which `check_stop` never stops a loop, and `None` (the default) to keep calling `check_stop`.

The policies must agree with `check_stop` for every row; `test/modular/test_stop_policies.py` checks the models that declare them.

A `TokenStop` with `runtime_check=True` declares them for you: its loop's stop ids, as `StopKind.EOS`, on `walk`; its `prefill_walks` keep `check_stop`.

### `cleanup_request` {#cleanup-request}

`cleanup_request(self, request_id)`

Free per-request state held inside the submodule when a request finishes: buffers, per-request caches, counters. See Qwen3-Omni's `Code2WavSubmodule` for an example.

### `filter_batched_output` {#filter-batched-output}

`filter_batched_output(...)` and `unpack_packed_outputs(...)`

Output fixups that run after the forward. A captured forward always emits the same set of keys, because the graph shape is fixed. Use `filter_batched_output` to drop keys that a particular request must not receive. Use `unpack_packed_outputs` to slice a packed `(total_tokens, ...)` tensor into per-request entries, when the slice boundaries depend on the real sequence lengths and therefore cannot be computed inside the captured region. Both methods are defined on `NodeSubmodule`, so any node can use them.

### `spanned_outputs` {#spanned-outputs}

`spanned_outputs(graph_walk) -> frozenset[str]`

Outputs whose valid length per row is known only on the device, such as audio with silence to trim. `forward_batched` returns a `BatchedModelOutput` whose `output_spans` maps the output's name to a `[bs, 2]` int64 tensor on the device: row `i` holds the first and one-past-last index of row `i`'s valid samples along the output's last dimension. A step that returns spans returns one for every output declared here, since per-request forwards are merged by name. The forward keeps a fixed width and does no host read. The worker cuts each row to its span after the step's completion event, before the stop check, transport or a streaming edge reads it. The cut is a view, not a copy. Engine-side `postprocess` still sees the uncut output. A row whose span is empty is left out of the store after the stop check, as a withheld output is (`StopCheck`): a streaming edge gets no item for it. A spanned output must not feed a node that the same worker speculates into.

Two more methods control batching and CUDA graphs: `can_batch` with `forward_batched`, and `get_accelerator_graph_configs`. See [batching and graph capture](/model_capture#step-5).

## Chunk long prompts

A walk with long prompts can run each across several steps, at most a token budget per step, so the decode rows batched beside it keep running. Each chunk is one iteration of a Loop around the node, which counts the tokens its chunks ran and ends at the prompt's length. To opt a walk in:

- `Model.get_chunking_policies()` returns `{node: (ChunkingPolicy, ...)}`, each policy naming the `walks` it covers. It is declared on the model, not the submodule, because the graph build reads it: `Model` wraps each chunkable node in its Loop wherever `get_graph_walk_graphs` is read, so the model returns its walks as usual. The fields:

  - `chunkable=True` lets the walk's rows be cut.
  - `max_batch_tokens`: the most tokens a step runs. A combined walk that carries chunked rows sets one too, since its steps run under it. Its step may pass it beside a speculation chain's decode rows, by at most those rows' tokens, and the engine trims a serving config's `prefill_token_buckets` assuming each such row runs one token. A walk whose decode rows run more (an MTP verify row's k+1) passes that bound, and its steps past a trimmed ladder's top run eagerly.
  - `accumulated_outputs`: output edges a consumer needs every chunk of. They arrive as one item per chunk, all when the prompt finishes.
  - `per_chunk_outputs`: streaming edges sent on every chunk as it runs, for a consumer that can start on a prefix. Any edge in neither set carries the final chunk's output alone.
  - `reuses_cached_prefix`: a callable saying whether a row may start past its cached prefix; `None` (the default) is always. Set it where a row may have to write its prefix again.
  - `reserve_whole_prefill` (default on): a row's first chunk reserves the state its whole prefill needs, so a part-done row cannot wedge on a full pool. Turn it off for a walk whose state grows by something other than the tokens a step runs.

  A resource that keeps state only on a grid counted from a chunk's start declares `Resource.chunk_alignment`, and a cut chunk of the node's rows is then a multiple of every alignment its resources declare (`Engine.chunk_alignment`). The chunk floor rounds up to it, and a budget under it fails loading.

  A streaming consumer of an accumulated edge whose `ChunkPolicy` expects one item (`FixedChunkPolicy(1)`, say) sets `Connection.join_dim`, so its `StreamBuffer` joins the pieces into that item. A consumer that can take the pieces as they come says so with `ChunkPolicy.allow_partial_input` (`FixedChunkPolicy(allow_partial=True)`), and the producer then sends the edge per chunk, as Qwen3-Omni's Thinker does into its Talker. A chunked stream its consumer would misread, each piece taken for the whole input, is refused at startup.

- `get_input_sequence_len(graph_walk, fwd_info, inputs)` gives a row's length from its input shapes, before `prepare_inputs` runs. The scheduler cuts the row by it, and a row whose prepared input turns out another length fails.

- `split_inputs(graph_walk, fwd_info, inputs, start, end)` cuts the whole prepared input to tokens `[start, end)`. `ARNodeSubmodule`'s default cuts the token ids or embeddings and any custom position ids, and refuses inputs it cannot see into (`tensor_inputs`, `kwargs`, `resource_step_info`).

Each chunk is a full forward, so it samples a token, but only the final chunk's token is real (`inputs.is_final_chunk`). The model need not handle that: the sampler commits no RNG offset or seen token for a row mid-prefill (it reads `StepContext.chunk_tokens_after`), the Loop carries only the final chunk's outputs, and the worker takes no stop or prefix key from a non-final chunk. `test/modular/test_chunked_prefill.py` and `test/modular/test_bagel_chunked_prefill.py` show how to test a chunking model. A deployment can change the budgets (see [chunked prefill budgets](/serving#chunked-prefill-budgets)).

## Declare resource effects for a step {#step-4a-declare-the-step}

`declare_step` tells the engine what one batched step does to the node's resources: which cache streams it touches, how much each stream grows, what the attention plan is based on, which streams fork, and what is committed after the forward completes.

The runner calls the declaration and the resource lifecycle around your forward:

```text
declare_step()  →  admit  →  plan  →  preprocess  →  forward  →  commit
```

The runner owns this lifecycle. A submodule that declares a step must therefore contain no plan calls and no advance calls of its own.

Declaring the work also lets the worker handle a cache that is full. If a step cannot be admitted, the engine returns an admit failure. The scheduler can then apply backpressure and evict other requests. Without a declaration, the same situation raises a `RuntimeError` inside the forward.

Returning `None` means that the submodule manages its own resources. This is the legacy path, kept for submodules that have not been migrated.

A walk named in `resident_walks()` runs its captured steps off per-request tables on the device instead of a plan rebuilt per step (`mstar/engine/resources/resident.py`). The walk must declare, for each resource, one stream that takes one token per row, or one it only reads at span 0 (a cross-attention context), with no forks, retention or sink, and its `preprocess` must read no planned position or KV location, because the captured graph fills those in first. Each KV pool of the node keeps its own block table and lengths; positions read the pool their `PositionConfig.kv_cache` names. Capture raises on a declaration that breaks this. The engine turns it on only if every resource of the node can (`Resource.resident_refusal`) and the deployment left `knobs: resident_planning` at `auto`; the worker log says why otherwise. A resource the node shares with other nodes is fine while they plan on the host (a sharer's host step marks the rows it moved, and an offload it causes frees the slot on every planner bound to the resource); it is refused if another sharer names resident walks too, or runs in lockstep. Steps of other walks, and eager steps, keep the host plan and leave the row stale, so the first resident step after them writes it. The sampler takes part on its own: its per-request scalars (temperature, top-k, top-p, seed, penalties) become cells of the row, so a resident step stages none of them, while the RNG offset, the last token and the repetition-penalty mask stay by the sampler's own row of each request.

A `SubmoduleStep` contains a list of `Segment` objects and one `ResourceStep` per resource key:

- `Segment(request_id, label, span)` is one request's contribution to one cache stream in this step. `span` is the number of tokens by which the stream grows. A `span` of 0 reads the stream without extending it: admission reserves nothing, and commit does nothing. A request contributes one segment per label that is active for it.
- The `segments` argument of `SubmoduleStep` is a default value. Any `ResourceStep` that does not set its own `segments` uses this list.
- `KVStep(commit=, eager_write=, combined_labels=, pre_forks=, post_forks=)`. See below.
- `AttentionStep(causal=, context_only=)` describes the attention plan. `context_only=True` has the queries attend to the stored context alone, not to the tokens this step appends, and the step's own `segments` then give the query counts. Only the MLA backend reads it; the others refuse it. A `RaggedAttentionSpec` steps through this same type. There, the segments are the whole layout rather than an extension of a cache. See [Cacheless attention (encoder towers)](/model_resources#cacheless-attention-encoder-towers).
- `PositionStep(pos_ids=, advance=)`. With `pos_ids=None`, positions are derived from the stream counters. Pass explicit ids, keyed by plan label, when the model computes positions itself.
- `SamplerStep(apply_penalty=, prefill_tracked_tokens=, loopback_writes=)`. `prefill_tracked_tokens` initializes the repetition-penalty mask with the prompt tokens. Only the prefill step passes them, because the sampler tracks every token it samples afterwards. `loopback_writes` names the declared loop-back states this step's forward stores (see [Device loop-back](/model_submodules#device-loop-back)).

The Orpheus declaration is the simplest form. It uses one label, computes spans directly from the prepared inputs, and steps all four resources together:

```python
def declare_step(self, graph_walk, request_ids, inputs,
                 slot_lease=None, piecewise_leases=None, **kwargs):
    prefill_tokens = {}
    if graph_walk == "prefill":
        prefill_tokens = {
            rid: inp.input_ids
            for rid, inp in zip(request_ids, inputs, strict=True)
        }
    return SubmoduleStep(
        segments=[
            Segment(request_id=rid, label="main", span=inp.input_seq_len)
            for rid, inp in zip(request_ids, inputs, strict=True)
        ],
        steps={
            KV_CACHE: KVStep(),
            ATTN: AttentionStep(causal=True),
            SAMPLER: SamplerStep(apply_penalty=True,
                                 prefill_tracked_tokens=prefill_tokens),
            ROPE: PositionStep(),
        },
    )
```

**Padding rows.** Under a captured graph, the batch is padded to the shape of the capture bucket, and `request_ids` also contains the ids of the padding rows. Declare segments for those rows in the same way as for real rows. The `zip(..., strict=True)` in the example above already does this.

**The two leases.** `slot_lease` is the CUDA-graph slot on which this step will replay. It is `None` for an eager step. If a submodule's declaration differs between the captured case and the eager case, it must check the lease, not its own capture key. The capture key only says that the batch could be captured. The lease says that the batch was captured. For example, Cosmos3 packs both guidance branches into a single plan for the captured shape, and uses the dense backend otherwise.

`piecewise_leases` names the inner regions of this node that hold their own slot for this step. Such a region declares, plans and commits its own work. Any resource that the region owns must therefore be excluded from the outer declaration. See [Capture an inner loop](/model_capture#piecewise-cuda-graphs-capturing-an-inner-loop).

**Advanced `KVStep` fields.** These fields cover cases that the engine previously handled as special cases. BAGEL uses all of them, in `mstar/model/bagel/submodules.py`:

- `commit=False`: the step reads and plans, but its writes do not become resident yet.
- `combined_labels={("main", "cfg_img"): "cfg_batched"}`: pack several labels into a single plan. Batched classifier-free guidance uses this to run two branches through one attention call. Positions take their packing from the KV plan, so the grouping is declared once here, and `PositionStep` keys its `pos_ids` by the combined label.
- `pre_forks` and `post_forks`: a value such as `(("main", "cfg_text"),)` forks one cache stream from another. `pre_forks` forks before any planning or writing, for a branch that must keep the context from before this step. `post_forks` forks at commit time, for a branch that must include this step's writes.
- `eager_write=True`: the step's tokens for this cache are written outside any captured graph, for example in `preprocess` before the replay. Their addressing stays an ordinary plan rather than the slot's static buffers, which are sized for the bucket's in-graph tokens. Whisper's prefill uses it to write its 1500-token encoder context while replaying a graph sized by its few prompt tokens.

**Writing K/V yourself.** A layer that writes its K/V inside a fused kernel of its own, rather than through `write_kv`, asks the KV resource where the step's tokens go: `kv.write_target(layer_idx, label)` returns `(layer cache, page of each token, slot in page of each token, number of tokens to write)` for the current plan (NHD layout only). Tokens past that number are the plan's padding and must not be written. The fused q/k norm, RoPE and KV-write kernels that Qwen3-ASR and Qwen3-Omni's Thinker call through `AttentionCallable.norm_rope_attend` and `norm_rope_table_attend` are the example.

**Testing.** `declare_step` performs only host-side bookkeeping, so you can unit-test it on CPU without model weights. `test/modular/vjepa2/fake_resources.py` shows how to stub the resources, and `test/modular/test_resource_runner.py` tests the runner's lifecycle directly.

### Reaching your resources {#reaching-your-resources}

Two places need access to resources, and each has its own mechanism.

**In the forward**, read `engine_inputs.resources`, keyed by `resource_key`:

```python
def _forward(self, graph_walk, engine_inputs, text_inputs):
    sampler: SamplerResource = engine_inputs.resources[SAMPLER]
    attn: AttentionManager = engine_inputs.resources[ATTN]
    hidden = self.language_model(self.embed_tokens(text_inputs), label="main")
    if graph_walk == "prefill":
        hidden = attn.select_last_hidden(hidden)
    return sampler.sample(engine_inputs.request_ids, logits=self.lm_head(hidden))
```

`ModelInputsFromEngine` carries six other useful fields:

- `step` is this step's `SubmoduleStep`. A forward that must match its own declaration reads it here instead of computing the same information again.
- `captured` is true when this forward runs under a CUDA-graph capture or replay. This field replaces the old `cache_manager.is_captured`. It is useful when `preprocess` packs its inputs differently for the fixed capture shape.
- `synthetic` is true when every row is a dummy request, during CUDA-graph capture or its warmup. Use it to keep statistics such as routing counts free of dummy traffic.
- `real_seq_len` is the token count of the real requests. Their rows come first; any rows after them are padding that a replay adds to reach the bucket shape. It is `None` when nothing was padded, so every row is real. Read it instead of assuming anything about the padding rows' own inputs.
- `per_request_states` is a `Mapping` that is resolved on first read.
- `piecewise_runners` holds the piecewise CUDA-graph runners, keyed by region name.

**In a layer**, resources are resolved once at load time. The engine calls `submodule.bind_node_resources(resources)`. That method stores the resources, then iterates over `self.modules()` and calls `bind_resources(resources)` on every module that defines it. A layer names the keys it needs in its constructor and resolves them in `bind_resources`. If a layer names a key that its node does not have, the error occurs at bind time rather than during a forward pass:

```python
ParallelAttention(..., attn_key=ATTN, kv_key=KV_CACHE, pos_key=ROPE)
```

Inside the layer, `AttentionCallable` (`mstar/engine/resources/convenience.py`) wraps the KV write and the attention call together. The label and the layer index are cursors stored on the resources. They are not passed as arguments on each call. The code that drives the layer stack binds the label once, then advances the index for each layer:

```python
def forward(self, query_sequence: torch.Tensor, *, label: str) -> torch.Tensor:
    self.layers[0].self_attn.attend.bind_step(label)
    for layer_idx, decoder_layer in enumerate(self.layers):
        decoder_layer.self_attn.attend.set_layer_idx(layer_idx)
        query_sequence = decoder_layer(hidden_states=query_sequence)
    return self.norm(query_sequence)   # the runner advances the cache, from the step
```

Cursors are used instead of arguments because passing the layer index as an argument makes inductor specialize on that integer. The frame is then retraced once per layer.

<a id="device-loop-back" style={{scrollMarginTop: "6rem"}} />

**Device loop-back.** A decode loop normally routes its sampled token back to itself as a tensor per request. An AR node that sets `self.device_loopback = DeviceLoopback(walk, signal, sampler, buffer)` instead reads each row's last sampled token off the sampler on the device (`MSTAR_DEVICE_LOOPBACK`): the base class's `device_loopback_signals` names the signal, so the worker routes it without a tensor and sends the client's copy inline, `prepare_inputs` returns `self.uniform_row_inputs(...)` for such a row, and `preprocess` reads the tokens with `self.loopback_inputs(engine_inputs, inputs)`. A row whose last step did not keep its value on the device (its first decode step, after the prefill) still brings it routed, and that read puts it over the slot's. `SampledTokenDecoder` declares it for Qwen3.5, Muse Glimmer, Higgs Audio, Qwen3-ASR and the Cosmos3 reasoner, and a node on it that reads the routed token sets `device_loopback = None`; Whisper and Qwen3-Omni's Thinker declare their own.

On such a node a captured step writes each row's token and RNG offset back to the request's row inside the graph (`knobs: sampler_ingraph_scatter`, on by default). Those rows are allocated once, `knobs: sampler_slots` of them, so a request takes its row when the runner admits it and waits while none is free, as it does for a recurrent state slot. A row the step drops (`SamplerStep(kept_rids=...)`) writes the trash row, so it keeps its offset.

State that a decode loop carries from step to step beside the token, such as Whisper's timestamp rule state, is declared on the sampler, not kept in the model (Whisper adds its signal to `device_loopback_signals` and passes its name to `loopback_inputs`):

```python
SamplerSpec(
    resource_key=SAMPLER, nodes={"decoder"}, vocab_size=vocab,
    loopback_state={"ts_rules": LoopbackState(
        width=4, dtype=torch.long, default=tuple(inactive_state()),
    )},
)
```

The sampler keeps one row per request by slot, grows it with its other per-request buffers, and resets a row to `default` when its slot is given to a new request. A step reads the rows with `sampler.loopback_state(name, request_ids)` in `preprocess` and stores the next ones from the forward with `sampler.store_loopback_state(name, request_ids, values)`. Under a CUDA-graph slot the store is captured into a per-step buffer and commit persists it, so the step must list the name in `SamplerStep(loopback_writes=...)`. An eager step writes the rows by request. Both paths address rows the same way, and the model never sees a slot index.

A kernel in the forward can draw its rows' tokens itself, as Qwen3-TTS's depth-loop kernel does for fifteen draws a step. `sampler.fused_draw_args()` returns the step's per-row temperature, top-k, top-p, seed and offset, in the forward's row order, and the kernel draws each row with `mstar.engine.resources.sampler.fused_draw.draw_row`, which picks the token `fused_sample` would. After the launch, `sampler.advance_offsets(draws)` moves the offsets as that many `sample` calls would. `fused_draw_args()` returns None when `sample` would do more than that draw (an eager step, the penalty, min-p, logprobs, a kept last token, a TP, SP or CFG node); the model then calls `sample`.

<Warning>

Where the callable is passed into a traced function, create one `AttentionCallable` per transformer, not one per layer. Dynamo specializes `ulysses_attention` on the identity of its `run_attention` argument. A per-layer callable therefore retraces that frame once per layer and exceeds the recompile limit. The shared `Attention` layer creates one callable per layer. That is safe only because the callable is never passed into a traced function.

</Warning>

### Loading weights {#loading-weights}

`get_submodule` loads a node's parameters. Weight loading is standardized through `mstar/model/loader/`. Use it instead of a custom `load_state_dict` call. Only then can the same code load both a single-GPU checkpoint and a tensor-parallel shard. See [Tensor parallelism](/model_deployment#tensor-parallelism). There are three layers:

1.  In `get_submodule`, build the `nn.Module` on the `meta` device, materialize it with `to_empty(device=...)`, then call `load_weights(module, source, device=...)` from `mstar.model.loader`. This function selects the correct safetensors iterator, for a single file or for a sharded Hugging Face directory, and then calls `module.load_weights(weights)`.
2.  Your module implements `load_weights(self, weights)` and delegates to `load_hf_weights(self, weights, stacked_params=..., name_remapper=...)`. That function streams the `(name, tensor)` pairs and dispatches each pair to the `weight_loader` of the matching parameter.
3.  `stacked_params` is a list of `StackedParamRule`. Each rule routes several checkpoint keys into one fused parameter, for example the Hugging Face `q_proj`, `k_proj` and `v_proj` keys into a single `qkv_proj` parameter. `LLAMA_STACKED_PARAMS` is a predefined rule set for Llama models. `name_remapper` rewrites or drops checkpoint keys that do not match your parameter paths.

```python
# in the Model: build on meta, materialize, hand off to the driver
def _create_llm_submodule(self, device, tp_group=None):
    from mstar.model.loader import load_weights
    with torch.device("meta"):
        language_model = OrpheusForCausalLM(self.config, comm_group=tp_group)
    language_model.to_empty(device=device)
    load_weights(language_model, local_dir, device=device)  # → module.load_weights(...)
    ...

# in the nn.Module: declare the fused-shard routing and delegate
def load_weights(self, weights):
    from mstar.model.loader import LLAMA_STACKED_PARAMS, load_hf_weights
    return load_hf_weights(self, weights, stacked_params=LLAMA_STACKED_PARAMS)
```

Each parameter's `weight_loader` also performs tensor-parallel sharding. When the module is built with a `comm_group` and `tp_world_size > 1`, the loader slices the incoming tensor along that parameter's shard dimension before copying it. For this reason, one `load_weights` path serves both single-GPU runs and tensor-parallel runs without change.

A quantized checkpoint is refused at load unless the model reads its format itself. Without this, a model that knows only unquantized weights would load fp8 values unscaled and drop the scales and packed weights, and then serve garbage. There are two checks:

- The safetensors iterators refuse a checkpoint that declares a quantization: `quantization_config` in `config.json` (HF fp8, AWQ, GPTQ, bitsandbytes, mxfp4, compressed-tensors, ModelOpt), ModelOpt's `hf_quant_config.json`, or AutoGPTQ's or AutoAWQ's config file.
- `load_weights_into` refuses a quantized weight's part, such as `weight_scale_inv`, `weight_scale`, `weight_packed` or `qweight`, when no parameter takes it.

A model that loads a format itself names its `quant_method`. GLM-5.2 and GLM-5.3-Flash, for example, pass `quant_methods=("fp8",)` to `load_weights` and to the iterators.
