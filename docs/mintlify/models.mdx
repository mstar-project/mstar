Choose a model by the task you need to serve, then open its guide for checkpoint access, dependencies, configuration, request options and limits. A registry key is the value of `model:` in a serving YAML file; the CLI maps model keys to deployment configs in `mstar/cli/main.py`. Checkpoints and classes are registered in `mstar/model/registry.py`.

Start with [Quickstart](/quickstart) for a first request. [Installation](/installation) covers dependencies, and [Serving](/serving) explains GPU placement. The config a model ships is a starting layout, not a hardware minimum: use the model's measured setup and capacity notes before changing GPU count, precision or concurrency.

## Compatibility and defaults

- Models marked *(Beta)* are functionally supported but not yet performance-optimized; treat their throughput/latency as provisional.
- The checkpoint IDs in the model guides are representative. You may use local paths or compatible variants.
- Some families accept multimodal input (image/audio/video); see the model's `process_prompt` for the inputs it expects.
- Models on the fused MoE kernel (Qwen3-Omni, Command A+) take their tiles from the `moe_gemm` table for the GPU (`mstar/kernels/tables/moe_gemm/`) when it has the expert shape, and default tiles otherwise. The server logs the sweep command for each shape it serves untuned; see "Tuned kernel configs" in [Adding a New Model](/adding_models).
- To add a new family, see [Adding a New Model](/adding_models).
- Unset sampling knobs take the checkpoint's `generation_config.json`, then the model's config. BAGEL and Orpheus are the exception: their files are the backbone's chat presets (Qwen2.5-7B-Instruct, Llama-3.2-3B), so only `do_sample: false` is read and the recipes stay (BAGEL temperature 0.6, top_k 0, top_p 1.0; Orpheus temperature 0.6, top_p 0.8).
