The `fdb` suite follows the reference runner (`benchmarks/duplex/fdb_v15`, pinned in `benchmark/eval/fdb_reference.py`) metric for metric, so its numbers can be compared with that runner's. v1.5 has 498 pairs in four categories: `user_interruption` (200), `user_backchannel` (98), `talking_to_other` (100) and `background_speech` (100). A pair is the user's query with a later overlapping event (`input.wav`) and the query alone (`clean_input.wav`); each is its own session.

## Prepare the dataset and judges

The example uses a local Qwen judge and an optional OpenAI judge. Start the local judge with the model, revision and settings in the comments before running `run fdb`. The OpenAI judge requires `OPENAI_API_KEY`; without it that judge is skipped and the report records why.

``` bash
python -m benchmark.eval data fdb-v15 --out ~/eval-data/fdb --per-category 12   # or all

# a local judge on the same GPU, started first so it gets a fixed share of memory:
# any OpenAI-compatible server for Qwen/Qwen3.8-27B at revision 1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0,
# served as qwen3.8-27b on port 30000 with a qwen3 reasoning parser, 42% of GPU memory
# and a 65536-token context

python -m benchmark.eval run fdb --serve nemotron_duplex \
    --data ~/eval-data/fdb/manifest-12.jsonl --concurrency 16 --repeats 3 --out results/fdb \
    --judge qwen=http://127.0.0.1:30000/v1 --judge-revision qwen=1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0 \
    --judge gpt4o=openai

python -m benchmark.eval report results/fdb --md fdb.md --chart fdb.png
python -m benchmark.eval agreement results/fdb --md agreement.md --chart confusion.png
```

## What each score measures

Each number is per category and for `all`, mean +- std over repeats:

- **Observation window.** The model's output over `[0, T]`, T the input length, as 16 kHz mono with exactly the input's sample count. A frame-synchronous model emits one output frame per input frame, so this is the audio a client would hear with no transport delay; a client that streams in real time and plays what arrives (as the reference runner does) also gets the server's processing and transport delay in its window. `wall_ms_per_frame` and `on_time_rate` show whether the server kept up live.
- **Stop and response latency.** The official `get_timing.py` on Silero VAD speech spans (`silero-vad` package, user spans merged across 0.6 s gaps, model spans across 0.5 s). Stop intervals are overlaps of user and model speech; response intervals run from the end of a user span to the next later model start. These are whole-file intervals of the overlap session, pooled: the mean over every interval of every timed session, null when there is none. Lower stop latency is better on `user_interruption`; on the other three categories the model should keep its turn, so the overlap mostly tracks how long the other speech lasts.
- **Behavior labels.** The four files of a pair are transcribed with word timestamps by the official ASR script on `nvidia/parakeet-tdt-0.6b-v2` (pinned revision and SHA-256; needs `nemo_toolkit[asr]`), then each judge labels the pair with the exact official prompt: `C_RESPOND` (addressed the overlap), `C_RESUME` (ignored it and continued), `C_UNCERTAIN_HANDLING` (asked for a repeat) or `C_UNKNOWN` (off-target or silent). The share that should be high is `C_RESPOND` on `user_interruption` and `C_RESUME` on the other three. Shares are over valid labels; `judged_pairs` says how many there were.
- **Semantic quality** (non-official, one local judge, as in the reference runner). Each pair is graded `accept`, `fail` or `unresolved` on `interaction_handling`, `relevance` and `grounding` with the reference judge's frozen prompt and schema (fetched at a pinned commit); `joint` fails if any axis fails and accepts only if all three accept. A verdict without an exact quote of its source becomes `unresolved`. `quality = A/(A+F)` and `coverage = (A+F)/N`, N every selected pair: read them together. Before grading, six frozen control cases must reproduce all 18 expected statuses, or the run is not graded (a rubric check, not judge accuracy).

Failed sessions stay in every denominator and are never timed or judged.

### Judges and agreement {#judges-and-agreement}

A judge is any OpenAI-compatible chat endpoint, named with `--judge NAME=...`:

- **local**: `NAME=http://host:port/v1` (any OpenAI-compatible server, M\* included if it serves the model). The model sent is the endpoint's `/v1/models` entry (`URL#name` picks one) and every reply must report it. Behavior labels decode as the reference judge does: non-thinking, temperature 0, top_p 1, 512 tokens, retry seeds 1 to 3. The semantic judge runs thinking mode, temperature 0, seed 1, in batches of 8 pairs; serve with a reasoning parser (`--reasoning-parser qwen3`) so the JSON answer arrives in `content`. `Qwen/Qwen3.8-27B` is the reference runner's choice.
- **API**: `NAME=openai` is `gpt-4o-2024-08-06`, the paper's judge, with the official decoding. It reads `OPENAI_API_KEY` (and `OPENAI_BASE_URL`) from the environment and is skipped, with the reason in the results file and the report, when the key is not set. Keys are never written anywhere.

Labels from different judges are kept apart (`<category>.<judge>.<label>`); compare runs only under the same judge. With two or more judges, every repeat also records `agreement.<a>.<b>.agreement` and `.kappa` (Cohen's) over the pairs both labeled validly, and `agreement` pools them over repeats into a confusion matrix with per-category agreement and each judge's label shares. The reference runner measured Qwen against gpt-4o on Nemotron VoiceChat (the model behind `nemotron_duplex`): 84.9% agreement, kappa 0.72, with Qwen giving far fewer `C_UNKNOWN` labels, so a local judge's numbers are for comparing like with like, and the API judge's for comparing with published results.

## Rejudge saved results

`rejudge` adds a judge to finished results from the transcripts they hold, without a server or GPU (for example once an API key is available), and recomputes the label and agreement metrics:

```text
python -m benchmark.eval rejudge results/fdb --judge gpt4o=openai --out results/fdb-gpt4o
```

`--semantic-only --semantic-judge NAME` regrades only the semantic A/F/U axes and keeps every judge's labels; `--retry-failed` relabels only the pairs whose label from an unchanged judge failed. Rate limits, server errors and dropped connections are retried with the same request and seed, with exponential backoff (`Retry-After` honored), so they never move the official loop to its next seed; a pair whose retries run out is `failed`.
