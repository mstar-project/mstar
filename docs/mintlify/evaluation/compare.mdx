---
title: "Compare a change with its base"
description: "Compare correctness, quality and performance between two revisions on the same hardware."
---

`compare` serves two revisions on the same GPUs and checks their outputs, quality scores and performance against the limits below. Run it from a checkout with the `eval` extra installed. The serving environment must have each selected model's dependencies, GPU capacity and checkpoint access.

Start with Kokoro, using the current checkout commit as the candidate:

``` bash
python -m benchmark.eval compare --base main --head HEAD \
    --models kokoro
```

The run writes `report/report.md`, `report/chart.png` and `report/summary.json` under its run directory. Read request errors and correctness verdicts before interpreting a performance difference. `HEAD` means the committed revision; commit changes you want to compare.

List the available models and cases before widening the run:

``` bash
python -m benchmark.eval compare --list
python -m benchmark.eval compare --base main --head HEAD --models tag:tts,qwen3_omni --rp
```

## Choose revisions and environments

`--head` and `--base` take a branch (fetched fresh from `mstar-project/mstar`, then `origin`), a PR number, a commit, or another local ref such as `HEAD` or a tag (this checkout's commit).

Both trees are exported from the checkout running `compare` (each arm imports its own tree and builds its own `rust/` extension, in one Python environment); the client, the checks and the report always come from that checkout, so `main` can be measured before it has this framework. Each model uses the GPU slots declared by its case entry (one by default): base and head run back to back, arm order alternating from model to model, every case at each concurrency in its `conc` with `repeats` passes after warmup waves.

`--sessions 2` runs two server sessions per arm (ABBA). Each arm's first server start gets twice the model's `startup_timeout_s`, since it may compile from cold caches whichever arm goes first; later starts get it once.

The `rust/` extension is built with the environment's `pip`, or `uv pip` when it has none (a uv venv); if a tree both arms share cannot be built, both run the environment's `mstar_rust` and the report says so.

Exported trees, `rust/` builds, local jobs' outputs and the inputs live in `--work-dir` (default `$XDG_CACHE_HOME/mstar-eval`, else `~/.cache/mstar-eval`; `--data-dir` moves the inputs alone).

## Run on remote hosts

With `--hosts`, idle hosts take whatever models are still queued; a host that stops answering is dropped and its model requeued. Hosts need key-based `ssh`, `rsync` at both ends, an M\* environment (`--host-python`) and the Hugging Face Hub (with a login for gated repos such as Orpheus) or a warm cache; their work directory is `--host-dir`. Machines that must be started first are a launcher's job: `--host-provider module:factory` supplies the hosts and is told when the run ends (`benchmark/eval/e2e/hosts.py`). For example, replace these hostnames and GPU slots with your own:

``` bash
python -m benchmark.eval compare --base main --head HEAD --models kokoro \
    --hosts bench@gpu1,bench@gpu2:1
```

## Select models and cases

The models and cases are `benchmark/eval/e2e/cases.yaml`: TTS, voice clone, ASR, duplex, text, image, audio and video in, speech out, image and video generation, streamed frames, VLA actions, and with `--rp` request-path cases and served invariants. Speech cases use the `tts`, `asr` and `duplex` suites; the rest use the `e2e` suite (`run e2e --kind chat_image|image|video|pi05|frames|world|...`). Some entries (including CosyVoice3, VoxCPM2, Omnilingual ASR and LingBot-World) are marked `optional: true` and excluded from `all`. Select them with `--models tag:new-model` or by name, against a base revision that serves them. Inputs are built once into `--data-dir` (`python -m benchmark.eval data e2e --out DIR`: Seed-TTS and LibriSpeech sets plus generated media).

## Multi-GPU configs

Tensor parallel, sequence parallel, split and disaggregated deployments (`whisper_large_tp2`, `qwen3omni_thinker_tp2`, `cosmos3_nano_sp2`, `qwen3tts_1p7b_split`, `orpheus_pd_disaggregated`, `qwen3omni_pd_disaggregated`) are optional entries with `gpus: N`: select them with `--models tag:multi-gpu`. Such a model runs on N GPU slots of one host at once (`--hosts user@gpu8:0-7`), and a host with fewer slots never takes it. Each case has a wall cap (`case_timeout_s`; 3600 s by default, 900 s on these entries), which has to sit well above the slowest normal case on the host: a case still running then has hung, its server's Python stacks are saved (`py-spy dump` when installed) to `stacks.txt`, a hung head fails the row and a hung base reports it broken. py-spy shows threads, not coroutines, so a hang at an `await` in the API server shows an idle event loop.

Where ptrace is restricted, `--stacks-sudo` retries the dump with `sudo -n`; it is off by default because a refused `sudo` is logged, and often mailed, on shared clusters.

## Worker-to-worker transport

The split and disaggregated configs also run over shared memory (`_shm`), Mooncake TCP (`_tcp`) and Mooncake RDMA (`_rdma`, skipped on a host without an RDMA device): select the first two with `--models tag:w2w` and RDMA with `tag:rdma`. Besides the multi-GPU cases, `cancel` drops a stream mid-transfer and `timeout` runs on a second server whose `--timeout` is shorter than one of its requests. After every case the server is checked: its processes still alive, no mstar `/dev/shm` entry left behind, no crash or transfer-failure line in its log. A finding head has and base does not fails the row; base crashing reports it broken.

## Read the verdict

The run directory holds every results file and `report/report.md` (a table for a PR body, details in toggles), `report/chart.png` and `report/summary.json`. `compare` exits with 1 when any row is flagged, else with 2 when any row has no verdict (its job failed or was interrupted, the model was skipped or never got a GPU, base is broken, or base answered no request at some server session and concurrency, whatever head did), else 0; on Ctrl-C it stops every job, prints one line and exits with 130. A row is **flagged** when:

- **correctness changed**: greedy text is neither identical (share at least `min_match`) nor close (median similarity 0.6 or more, length ratio 0.8 to 1.25), or any head reply is base's cut below 80% of its length (empty replies included); speech WER (Whisper large-v3 round trip for TTS) rose more than `max_increase` points; a seeded image, video or frame stream fell below `min_db` PSNR against base; VLA actions moved more than `tol`; duplex take-turn or yield rates dropped more than `tol`; a request-path status code changed; head had more request errors than base; or head answered no request at a server session and concurrency where base answered some (request errors per arm are a column of the main table). A greedy-text failure on its limit alone (no missing, cut-short, undecodable or reshaped outputs, no extra errors) whose `quality` scores all hold reads "changed, quality same" instead and is not flagged. A PSNR failure stays flagged whatever its CLIP score: a seed the server stops honouring changes the pixels, not their quality;
- **quality worse**: a `quality` score of the case (`mos`: UTMOS22 of the speech; `speaker_sim`: WavLM similarity to the reference clip; `clip`: CLIP score of the image or video against its prompt; each arm scored on its own c=1 outputs after the servers stop) is below base's by more than 1.5 times the row's A/A swing, and at least 0.1 UTMOS, 0.02 similarity or 0.5 CLIP points;
- **a regression**: c=1 latency or c=max throughput is worse by more than 5%, by more than two combined standard deviations of the passes, and by more than 1.5 times the largest drift that row showed between two server processes of identical code in its last 8 A/A runs (its A/A noise floor; a lone drift over 10% and over three times the median of the others is left out until a second run agrees). When base and head return different output lengths for the same requests, latency is compared over the requests whose lengths matched, else per token or audio second;
- **head does not build** (its `rust/` extension or Rust frontend) while base does, or **head does not start** while base does.

A perf row flagged with one session per arm is rerun with two (ABBA) before it is reported, since a server process can settle at one of two speeds; `--no-rerun` turns that off.

## Calibrate with identical-code runs

Noise floors, correctness swings and quality-score swings come from A/A runs (base and head the same commit), per GPU type, in `benchmark/eval/e2e/calibration.yaml`; each kind keeps its own list of folded runs (`_runs`, `_runs_correct`, `_runs_quality`), so a run folded before a kind existed can still add it. After a large change on `main`, a new model, or on a new GPU type, run `compare --base main --head main` for the models concerned, then `python -m benchmark.eval calibrate <run dir>`; rows without a floor on the run's GPU are named in the report and judged on the passes' spread alone. A calibrated swing only widens a `cases.yaml` limit, never tightens it. Rows of the A/A run that failed or had request errors stay out of the floors; `calibrate` prints how many per model.

## Run request-lifecycle stress workloads

`--stress` replaces the cases with a workload for load-dependent races, on the models whose `cases.yaml` entry has a `stress:` block (`qwen3_5_2b`):

```text
python -m benchmark.eval compare --base main --head HEAD --stress                  # 20 runs per arm of 60 s
python -m benchmark.eval compare --base main --head HEAD --stress --stress-runs 60 --stress-clients 32
```

Each run has `--stress-clients` clients (32), each holding one pinned `request_id` on streamed `/generate` and mixing five patterns: close at a random chunk, close before reading, close then retry at once under the same id, reuse after a full read, and a second request while the first streams (one of the pair should get a 409). A run fails on a hang (no progress for `--stress-hang-s`, 30 s), a 5xx, unexpected 4xx, empty reply or in-band error, cross-talk (a reply holding another prompt's answer), the server's own M\* tensor files left in `/dev/shm` 30 s after the run (other servers on the host use another deployment token or pid, so theirs are not counted), or a server process that exits.

Every 5 runs get a fresh server, arms alternated. Head is flagged when it crashes or shows cross-talk and base never does, or when its failed-run count beats base's at one-sided Fisher exact p \< 0.05; the report states N and the smallest gap N can detect (`--stress-runs 20`: 0 against 5 failed runs). When base fails every run, no head count can beat it, so read the per-pattern request outcomes in the report's toggle instead. `--stress-patterns` picks a subset (`barge_in,drop,retry,reuse,overlap`). The code is `benchmark/eval/e2e/stress.py`.
