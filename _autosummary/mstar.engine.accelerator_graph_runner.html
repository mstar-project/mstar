plan_stream()[source]#

Dedicated stream for pre-planning.

Pre-plan must not submit onto the default stream: whether its memcpys land before or after the GPU thread records the previous batch’s completion event is timing-dependent, and landing after delays that event past pre-plan’s own kernels. Its own stream keeps the two independent; a plan-done event gates the replay that reads the buffers.

select_batched_bucket(graph_walk, bs, cg_key_info=None)[source]#

A bucket for a batch whose inputs aren’t built yet.

Only a batched capture can answer this: its token count is a property of the config (bs rows of a fixed per-request length), so the bucket follows from the batch size alone. A packed capture’s token count is a property of the requests, so it has to wait for prepare_inputs and go through select_bucket.

size_captures()[source]#

Warm every spec up, and capture each walk’s largest buckets once, thrown away, before any runner captures for real.

Every bucket is warmed rather than the first in capture order: that order leads with batch size, so it can open on a decode bucket while a one-row prefill of thousands of tokens peaks far higher. And every slot: a slot’s first plan builds state of its own (FlashInfer’s graph wrappers and their workspace, 750 MiB for the Talker’s second slot), which has to be spent before free memory is read.

Return type:

dict[BucketKey, CaptureCost]

size_lent_captures(wanted)[source]#

Capture every bucket a lender sized, thrown away, if wanted here or on another rank: a plan that leaves graphs out needs what each takes, not what its walk’s largest does.

Every rank asks, so the ranks of a group size again together or not at all, and plan on the same kind of cost. With no forward and no barrier: sizing ran the forwards, and a capture runs no collective.

class mstar.engine.accelerator_graph_runner.ExecutableMemory[source]#

Bases: object

The executable memory a walk’s graphs take per node, outside any pool, measured on copies of its first throwaway graph: executables instantiated from it through libcuda. The cost per node changes with a graph’s size, even for the same kernels: a chain of adds takes 3.1 KiB a node at 300 nodes and 2.4 at 2222. A walk’s graphs are about the same size, so the first graph’s cost per node holds for all of them.

The copies are held until the runner captures. The driver keeps a destroyed graph’s executable memory to reuse, and maps new memory beside it, so after any destroy, free memory drops by less than a copy takes.

measure(graph, nodes)[source]#

Set per_node and held from copies of graph, held until release.

The count starts after the first copy that takes free memory, since copies until then fill pieces the driver mapped earlier. It adds one 2 MiB piece, since the first counted copy may start partway into a piece. Free memory is the device’s, so another process allocating or freeing moves it: a count is kept only if free memory never rose and no copy took more than two pieces above the mean. If no count is kept, per_node is the largest rate a count gave. None if no copy could be counted.

mstar.engine.accelerator_graph_runner.capture_into_graph(run, pool, device, autocast_dtype, keep_graph=False)[source]#

Capture run into a new CUDA graph allocated from pool.

Returns the graph and what run returned. A capture that fails part way leaves two things behind that would sink every later capture on the same pool: the caching allocator keeps routing this thread’s allocations into the pool (the next capture_begin fails with “already recording to mempool_id”), and torch.cuda.graph never switches the thread back off its capture stream. Undo both before re-raising, so the buckets after a failed one still capture and the thread keeps running on the stream it came in on.

A torch.compile’d forward that would recompile inside the capture is failed up front with the guard that broke: dynamo saves the CUDA RNG state before it compiles, which CUDA refuses during capture, so such a capture cannot succeed and would otherwise die with an unrelated error.

Parameters:

  • keep_graph (bool)

mstar.engine.accelerator_graph_runner.capture_with_static_outputs(run, warm_outputs, pool, device, autocast_dtype, keep_graph=False)[source]#

Capture run so its outputs land in buffers allocated OUTSIDE pool.

warm_outputs is what run returned on a warm-up call ({name: Tensor}); it fixes the shapes and dtypes. The captured graph ends with a device-to-device copy of each output into a buffer allocated here, before the capture, from the ordinary allocator.

Why not hand out the graph’s own output tensors: blocks a graph frees while it is being captured go back to the pool and are handed to the graphs captured after it, so an output that lived in the pool could sit exactly where an earlier-captured graph keeps its scratch and be overwritten by that graph’s next replay. That is harmless while a pool belongs to one region whose graphs replay one at a time and whose outputs are consumed before the next replay, but not once a node’s regions share one pool and replay in data-dependent order. Buffers outside the pool stay valid until this graph’s own next replay, whatever else the node runs in between.

  • keep_graph (bool)

mstar.engine.accelerator_graph_runner.plan_captures(pools, free, reusable=None)[source]#

The cheapest buckets across every pool on a device, added while the largest eager step still fits in free beside them.

A pool’s graphs, captured largest first, reuse its memory: it holds what every graph keeps, plus the most any one graph needs beyond that. So a bucket adds its slots’ kept bytes, and whatever it needs past the pool’s most so far. That is a model; the boot log compares it with what capture took. A bucket also adds its slots’ executable memory, less the memory its graphs reuse from the walk’s copies. A walk’s copies pay for its planned graphs’ executable memory once, across all its buckets. reusable bounds the reuse summed over all buckets, None for no bound.
