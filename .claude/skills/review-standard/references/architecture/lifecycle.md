# Request lifecycle and transport mechanisms on main

Checkout: main at `fa381afd6`. Paths are relative to the repo root. "Invariant N" means item N of the "Invariants" section of `AGENTS.md`. After the first full path in a block, a bare `file.py:line` or `:line` refers to the same file.

## Lifecycle, for orientation

The HTTP handler calls `APIServer.submit_request` (`mstar/api_server/entrypoint.py:536`), which hands a `PreprocessInput` to the data worker thread. The data worker stores and persists the input tensors and sends NEW_REQUEST to the conductor (`mstar/api_server/data_worker.py:660-691`). The conductor admits it and sends one NewRequest per worker and partition (`mstar/conductor/conductor.py:1286-1328`). Workers run the walk and report each pass with WORKER_GRAPHS_DONE, the conductor advances the walk or ends it, and workers send client outputs to the API server as RESULT_TENSORS. On completion the conductor sends `request_complete` with the output chunk counts and waits for the data worker's READS_DONE before it sends REMOVE_REQUEST to every participant. Abort and failure go through the same barrier with a DRAIN_REQUEST first.

### ZMQ control mesh and wire codec
- **Does:** Carries every control message between `api_server`, `api_server_preprocess_worker`, `conductor` and `worker_N`, one PULL inbox per entity with PUSH sockets to each peer, encoded as typed msgpack.
- **Where:** `make_communicator` (`mstar/communication/communicator.py:228`) picks `ZMQCommunicator` (`communicator.py:115`) or `RustZMQCommunicator` (`mstar/communication/rust_communicator.py:44`) by `MSTAR_RUST_ZMQ`. Entry points are `send` (`communicator.py:183`), `get_all_new_messages` (`:197`), `poll_for_messages` (`:168`) and `register_event_for_poll` (`:159`) with `EventWakeup` (`mstar/communication/event.py:5`). The codec is `default_codec` (`mstar/communication/codec.py:87`) over `wire.encode` and `wire.decode` (`mstar/communication/wire.py:523`, `:561`), with tags in `_TYPES` (`mstar/communication/wire_types.py:62`). The vocabulary is `WorkerMessageType` and `ConductorMessageType` (`mstar/utils/ipc_format.py:33`, `:218`).
- **Keeps:** One inbox per entity, and the worker relies on per-link FIFO order between the conductor and itself (`mstar/worker/worker.py:933-937`). A frame that fails to decode is logged and dropped without losing the rest of the drained batch (`codec.py:68-84`). Both transports share endpoints and codec, so they mix per process (`communicator.py:239-241`). Over IPC the conductor takes an `flock` so a second deployment on the same prefix fails at start (`communicator.py:58-93`).
- **Used by:** `Conductor.__init__` (`conductor.py:577`), `Worker.__init__` (`worker.py:469`), `PreprocessWorker.__init__` (`data_worker.py:181`), `APIServer.__init__` (`entrypoint.py:391`), the graph runtime's sends (`mstar/graph/runtime/python.py:1574`, `:1620`). `RustFrontendBridge` (`mstar/api_server/rust_frontend.py:137`) uses the same transport with `MsgpackCodec` on a private socket dir.
- **Extend via:** A new message is a `MessageBody` dataclass in `ipc_format.py`, a new enum member, a tag in `wire_types.py:62`, and a branch in the receiver's dispatch: `Conductor._route_message` (`conductor.py:1922`), `Worker._process_message_list` (`worker.py:1240`), `PreprocessWorkerThread._process_messages` (`data_worker.py:1148`) or `APIServer._process_messages` (`entrypoint.py:722`). The tempting duplicate is a second socket, queue or side channel between two entities that already talk, which gives up the per-link order teardown depends on.
- **Breaks if:** A receiver lacks a branch for the new type. The conductor raises at `conductor.py:1964` and fails the named requests, but `Worker._process_message_list` has no `else` and drops it silently. A wire-format change must also land in the Rust transport and runtime (Invariant 5). Tensors in a control field are refused at send (`wire.py:507-511`), as is any other unsupported type (`wire.py:512`).

### Conductor admission and dispatch
- **Does:** Takes a NEW_REQUEST, queues it at `max_concurrent_requests`, picks workers for each worker graph, resolves the request's sharding and resource configs, and sends one NewRequest per worker and partition.
- **Where:** `Conductor._ingest_request` (`mstar/conductor/conductor.py:1069`), `_admit_request` (`:1110`), `_do_ingest_request` (`:1156`), `_try_admit_waiting` (`:1055`), `_reject_request` (`:1139`). Placement is `_assign_worker_graphs_to_workers` (`:866`), `_build_request_sharding_config` (`:899`) and `_split_inputs_to_workers` (`:922`). State is `RequestData` (`:301`).
- **Keeps:** A request stays in `self.requests` until `_finalize_draining` pops it (`conductor.py:1441`), so a draining request still counts toward the cap. A failure before `dispatched` is set (`:1286`) is a reject that only hard-removes the data worker's inputs (400 for `ValueError`, else 500). After it, the failure is a drain-barrier teardown (`:1121-1137`). Worker graphs that share a `_group_id` land on one DP replica, and a lockstep worker graph goes to a whole TP×SP instance (`:879-896`).
- **Used by:** `_route_message` (`conductor.py:1928`), `_finalize_draining` (`:1443`). Workers take the result at `Worker._add_new_request` (`mstar/worker/worker.py:819`).
- **Extend via:** Per-request validation goes before `dispatched = True` and raises `ValueError` so it becomes a 400, as `_max_output_tokens` (`conductor.py:583`) and `_loop_caps` (`:597`) do. A placement policy replaces `_assign_worker_graphs_to_workers` (its TODO at `:874-876`). Per-request resource knobs come from `Model.get_request_resource_configs` (`mstar/model/base.py:787`) and ride `CurrentForwardPassInfo.resource_configs` (`mstar/conductor/request_info.py:45`). The tempting duplicates are a second admission cap in the API server or worker, and a reject path that sends `request_failed` without the data worker's REMOVE_REQUEST, which leaks the persisted inputs.
- **Breaks if:** New pre-ingest state is not cleared on the abort-before-ingest path (`conductor.py:1077-1087`) or on reject (`:1146-1147`). A silent early return in `_do_ingest_request` after `self.requests[...]` is set (`:1228`) leaves a counted request with no teardown, since only exceptions reach `_admit_request`'s handler.

### Graph-walk transitions and partition completion
- **Does:** Counts WORKER_GRAPHS_DONE per worker graph and rank, and when a partition's walk is complete asks the model for the next walk, then sends its inputs, sends producer_done downstream, or ends the partition.
- **Where:** `_process_worker_graphs_done` (`mstar/conductor/conductor.py:1635`), `_process_done_forward` (`:1726`), `_send_partition_inputs` (`:1817`), `_send_producer_done` (`:1853`), `_set_partition_worker_graph_ids` (`:1352`), `_process_request_done` (`:1582`), driven from `run` (`:2068-2091`). State is `PartitionState` and `StreamingConnectionState` (`mstar/conductor/request_info.py:116`, `:102`). Model hooks are `get_initial_forward_pass_args` and `get_partition_forward_pass_args` (`mstar/model/base.py:821`, `:1072`) returning `ForwardPassArgs` (`base.py:414`).
- **Keeps:** A worker graph is complete only when every assigned rank has reported (`conductor.py:1711-1717`). Replicated fields (new-token counts, stream consumption) are read only from the `is_first_tp_rank` report (`:1694-1709`), while sharded ones (persist signals, publish info, chunk counts, stream items) accumulate from every rank. Reports for an unknown or draining request are ignored (`:1948`). A request is done only when every partition `is_done` (`:1815`), and `request_complete` goes out once (`completion_sent`, `:316`).
- **Used by:** `Conductor.run` (`conductor.py:2070-2091`). Workers send the reports from `PythonGraphRuntime._send_worker_graphs_done` (`mstar/graph/runtime/python.py:1584`) or the Rust runtime's `send_outputs` (`mstar/graph/runtime/rust.py:661`), and receive next-walk inputs at `Worker._process_new_inputs` (`mstar/worker/worker.py:1134`).
- **Extend via:** A new walk order, stop rule or per-walk kwargs belongs in the model's `get_partition_forward_pass_args`, through `inputs`, `request_done`, `step_metadata` and `unpersist_tensors`. Per-pass facts from workers ride a field on `WorkerGraphsDone` (`mstar/utils/ipc_format.py:243`). Cross-partition coordination uses streaming connections and producer_done (Invariant 12, including the #385 note). The tempting duplicate is a worker-side "request finished" message or a second completion counter beside `wg_rank_completions`.
- **Breaks if:** A new `WorkerGraphsDone` field is taken from every rank when ranks replicate it, or only from rank 0 when ranks shard it. The `max_output_tokens` cut (`conductor.py:1772-1777`) relies on rank-0-only counting.

### Persisted signals across walks
- **Does:** Keeps tensors a later walk needs (the request's inputs and outputs routed as persist) alive on their producer, with the conductor tracking how many readers each was sent to, and releases them with one UNPERSIST_TENSORS per producer.
- **Where:** `RequestData.persist_signals` and `persist_signal_ref_cnt` (`mstar/conductor/conductor.py:303-304`), `_update_persist_ref_counts` (`:1014`), `_un_persist_tensors` (`:1025`), `RequestData.remove_persist_signal_uuids` (`:345`). Producers handle the message at `Worker._unpersist_tensors` (`mstar/worker/worker.py:1227`) and `PreprocessWorkerThread._process_messages` (`mstar/api_server/data_worker.py:1158-1162`). The flag is `TensorCommunicationManager.set_persist` (`mstar/communication/tensors.py:1557`).
- **Keeps:** A persisted tensor is never collectable (`can_gc` needs `not persist`, `mstar/communication/tensor_store.py:376-378`) until UNPERSIST_TENSORS adds back the count of readers the conductor dispatched it to and clears the flag, so the producer frees it after the last of those readers acks. Ingest unpersists only after every NewRequest is out, so the count covers every worker and partition (`conductor.py:1332-1337`). Completion unpersists whatever is still held before the drain (`:1609-1617`).
- **Used by:** `_do_ingest_request` (`conductor.py:1300`, `:1334`), `_send_partition_inputs` (`:1831`), `_process_done_forward` (`:1802`), `_process_request_done` (`:1617`). Worker persists arrive in `WorkerGraphsDone.persist_signals` (`:1683-1685`). The data worker persists every input at `data_worker.py:671-673`.
- **Extend via:** A model releases a held signal by listing it in `ForwardPassArgs.unpersist_tensors`. A worker persists an output through the routing (`routing.persist`, `mstar/graph/runtime/python.py:1494-1495`), which reaches the conductor in the next WORKER_GRAPHS_DONE. The tempting duplicate is a worker-side cache of an earlier walk's tensors, or an extra ref taken by hand to keep one alive.
- **Breaks if:** An edge holding a persisted tensor is sent to a worker without `_update_persist_ref_counts`. The unpersist count is then short and the producer can free the tensor before the last reader's ack.

### Two-phase teardown barrier
- **Does:** Tears a request down in two phases: DRAIN_REQUEST makes each participant stop starting reads and send READS_DONE once its in-flight reads finish, and only then does the conductor send REMOVE_REQUEST to every participant and, on the fail path, `request_failed` to the client.
- **Where:** Conductor `_remove_request` (`mstar/conductor/conductor.py:1551`), `_register_draining` (`:1371`), `_handle_reads_done` (`:1445`), `_finalize_draining` (`:1413`), `_sweep_expiry` (`:1466`), `DrainingRequest` (`:364`), TTL `MSTAR_DRAIN_TTL_S` default 120 s (`:421`). The happy path registers at `_process_request_done` (`:1628-1633`). Worker side: `_drain_request` (`mstar/worker/worker.py:1026`), `_begin_drain` (`:1045`), `_complete_drain_if_ready` (`:1078`), `_apply_pending_drains` (`:1108`). Data worker: `_finish_reading` (`mstar/api_server/data_worker.py:1179`), `_begin_drain` (`:1192`), `_complete_drain_if_ready` (`:1198`), `_hard_cleanup` (`:1222`). Messages: `DrainRequest`, `ReadsDone`, `RemoveRequest` (`mstar/utils/ipc_format.py:72`, `:274`, `:62`).
- **Keeps:** No participant force-drops a request's tensors (`force_cleanup_request`, `mstar/communication/tensors.py:1656`) until every expected reader has sent READS_DONE. A READS_DONE that beats registration is applied when it registers (`conductor.py:1378`). The TTL forces a stalled barrier through and logs who never answered (`:1471-1481`). On the happy path only the data worker is awaited, and the NOTE at `:1623-1627` says worker reads past completion are not waited for. TP followers ignore the conductor's DRAIN and act on rank 0's forward, and every rank sends its own READS_DONE (`worker.py:1031-1069`).
- **Used by:** `_abort_request` (`conductor.py:1549`), `_fail_requests` (`:1511`), `_admit_request` (`:1134`), `_fail_after_error` (`:1979`), `_process_request_done` (`:1629`). The data worker starts its own drain on abort (`data_worker.py:937-950`), and `APIServer._prune_recently_completed` starts the happy-path READS_DONE (`mstar/api_server/entrypoint.py:718`).
- **Extend via:** A new entity that reads a request's tensors joins `participants` in `_remove_request`, answers DRAIN_REQUEST with READS_DONE gated on its own `has_inflight_reads` (`tensors.py:1615`), and does its hard cleanup on REMOVE_REQUEST. A new reason to end a request calls `_remove_request` with `failure_error`. The tempting duplicates are a REMOVE_REQUEST or `request_failed` sent outside the barrier, and a per-participant timeout beside `_drain_ttl_s`.
- **Breaks if:** A DRAIN reaches a participant after its REMOVE (the drains are sent before registering for this reason, `conductor.py:1561-1565`), or a worker ACKs while a committed TP-follow batch for the rid is still queued (`worker.py:1090-1096`). `_fail_all_requests` (`conductor.py:842`) is the one deliberate bypass, for a deployment going down.
- **See also:** `worker-scheduling.md` › Teardown ordering: admit fence, deferred removes, drains, `lockstep.md` › 12. Admit fence, `lockstep.md` › 13. Stamped teardown ordering, Worker removal sequencing.

### Request failure reporting and fatal shutdown
- **Does:** Routes every per-request failure to the client as one `request_failed` or error chunk and frees the request through the barrier, and turns a dead worker or conductor into a 503 for every waiting client followed by shutdown.
- **Where:** Worker `_fail_requests` (`mstar/worker/worker.py:4193`) sending FAIL_REQUESTS (`mstar/utils/ipc_format.py:282`), `_handle_main_loop_error` (`worker.py:4104`), `_drop_failed_rids` (`:4072`), `_handle_unservable` (`:2292`), per-rid failures in `run` (`:4676-4685`), ingest failure (`:848-853`), and the scheduler gate `MicroScheduler.fail_rids` (`mstar/worker/micro_scheduler.py:1315`). Conductor `_fail_requests` (`mstar/conductor/conductor.py:1494`), `_fail_after_error` (`:1966`), per-message isolation in `run` (`:2057-2091`), `_poll_worker_liveness` (`:810`), `_fail_all_requests` (`:842`), `DeadWorkerError` (`:69`). Data worker `_fail_request` (`mstar/api_server/data_worker.py:887`) and `_abort_failed_request` (`:923`). API server `_fail_pending_for_dead_conductor` (`mstar/api_server/entrypoint.py:480`). Orphan watchdogs are `_exit_when_orphaned` (`conductor.py:147`) and `watch_parent` (`entrypoint.py:123`).
- **Keeps:** A worker reports a rid and stops scheduling it, but keeps its state until the conductor's REMOVE (`worker.py:4211-4222`). Only the first report of a request is acted on, since every TP rank reports the same failure (`conductor.py:1500-1508`). A request whose `request_complete` already went out is torn down with no failure sent (`:1980-1984`). A message that raises fails only the requests it names (`:2063-2066`).
- **Used by:** The error sites above. The client sees the error at `APIServer._process_messages` (`entrypoint.py:789-813`) or as an error chunk (`:902-924`).
- **Extend via:** A worker stage that can blame specific rids puts them in `ExecutingBatch.failed_requests` (read at `worker.py:4676`) or calls `_fail_requests({handle: message})`. A data-worker stage calls `_fail_request`. A conductor stage raises inside `_route_message` or a run-loop stage and lets `_fail_after_error` handle it. The tempting duplicates are a worker sending `request_failed` to the API server, and a worker tearing a failed request down locally.
- **Breaks if:** A torn-down rid is reported, which would leave it in `failed_rids` with no REMOVE to clear it (`_fail_requests` filters these at `worker.py:4202-4205`). A batch-level raise fails every rid the iteration touched, by design (`:4113-4119`).

### Worker removal sequencing
- **Does:** Applies REMOVE_REQUEST on a worker in a safe order: deferred while an in-flight step or speculation holds the rid, replayed on TP followers in rank 0's order and step position, then purging engine, scheduler, tensor and graph-runtime state with the handle released last.
- **Where:** `Worker._remove_request` (`mstar/worker/worker.py:929`). Deferral is `_pending_removes` (`:639`) applied by `_apply_pending_removes_safe_to_drop` (`:4054`). TP ordering is `RemoveRequest.after_tp_seq` (`mstar/utils/ipc_format.py:68`), `_removal_step_reached` (`worker.py:4033`), `_removes_awaiting_step` (`:643`) and `_apply_removes_whose_step_landed` (`:4041`). The run loop calls these at `:4533`, `:4550`, `:4784` and `:4788-4794`.
- **Keeps:** Nothing an in-flight GPU step reads is torn down under it (`worker.py:960-974`). A follower acts only on rank 0's forwarded REMOVE, in rank 0's order and after the step rank 0 stamped (Invariant 11). `_graph_runtime.remove_request` runs last because it frees the handle (`:1023-1024`).
- **Used by:** `_process_message_list` (`worker.py:1277`). The scheduler reads `pending_removes` by reference (`worker.py:657`, `mstar/worker/micro_scheduler.py:695`), and `_is_tearing_down` (`worker.py:2654`) keeps speculation off removed, failed or draining rids.
- **Extend via:** New per-request worker state is purged inside `_remove_request` before the handle release. New "skip this rid" logic asks `_is_tearing_down`. The tempting duplicates are a clear at the top of a per-step routine and a second deferral queue for some new message.
- **Breaks if:** A teardown runs while the step's admit is outstanding (the loop fences with `_await_admit_settled` first, `worker.py:4531`, Invariants 7 and 11), or a follower tears down ahead of a removal it deferred earlier (`:966-974`).
- **See also:** `worker-scheduling.md` › Teardown ordering: admit fence, deferred removes, drains, `lockstep.md` › 12. Admit fence, `lockstep.md` › 13. Stamped teardown ordering, Two-phase teardown barrier.

### Late messages for unknown and torn-down ids
- **Does:** Parks INPUT_SIGNALS, STOP_LOOPS and forwarded REMOVE messages for a request this worker has no handle for until its NEW_REQUEST arrives, and drops them instead, acking any tensors unread, when the id is one of the last 4096 torn down here.
- **Where:** The park-or-drop branch of `Worker._process_message_list` (`mstar/worker/worker.py:1254-1271`), `_unprocessed_messages` (`:619`), `_process_unprocessed` (`:896`), `_removed_rids = RecentSet(_REMOVED_RIDS_KEEP)` (`:623`) with `_REMOVED_RIDS_KEEP = 4096` (`:112`), `_mark_removed` (`:904`), `_drop_for_removed` (`:916`) and `TensorCommunicationManager.ack_unread_tensors` (`mstar/communication/tensors.py:1341`). `RecentSet` is FIFO-evicting (`mstar/utils/containers.py:12`). The data worker acks late outputs at `PreprocessWorker.new_result_tensors` (`mstar/api_server/data_worker.py:278-283`), and the API server discards them at `entrypoint.py:838-856`.
- **Keeps:** A message for a torn-down request never waits for a NEW_REQUEST that will not come, and its producer still gets the ack that frees its buffers. The conductor's own REMOVE is never parked (`worker.py:1254-1259`), and `_remove_request` marks an unknown id removed (`:930-940`). The comment at `:105-111` states the bound's assumptions: a late message trails its teardown by far fewer than 4096 teardowns, and each submission key is unique, so a remembered id never gets another NEW_REQUEST.
- **Used by:** `_process_messages` (`worker.py:1294`), `_add_new_request` (`:894`), `_remove_request` (`:938`, `:1008`).
- **Extend via:** A new per-request message type that can outlive its request goes into `msg_types_needing_active_request` (`worker.py:1241-1245`), and into `_drop_for_removed` if it carries tensor descriptors. The tempting duplicate is a time-based tombstone or a second remembered-id set beside `_removed_rids`.
- **Breaks if:** A message lands after more than 4096 later teardowns. The id has left `_removed_rids`, so the message is parked in `_unprocessed_messages`, which has no bound or expiry in the code read.

### Tensor transport backends and reads
- **Does:** Moves tensor bytes out of band of the control mesh: the producer stores and registers a tensor and ships a `TensorPointerInfo`, and the consumer reads it over Mooncake RDMA or TCP, a per-uuid file under `/dev/shm`, or the Rust SHM arena.

### API server submissions, result delivery and disconnects
- **Does:** Gives each submission a never-reused key `<request_id>#<n>`, hands it to the data worker, collects result chunks on a message thread, holds a finished request open until every counted chunk has arrived, and aborts the submission when the client disconnects or times out.
- **Where:** `APIServer.submit_request` (`mstar/api_server/entrypoint.py:536`, key at `:585`), `wait_for_request_id` (`:624`), `PendingRequest` (`:236`), `_process_messages` (`:722`), `_prune_recently_completed` (`:664`), `_iter_result_chunk_batches` (`:990`, abort in its `finally` at `:1082-1084`), `collect_results` (`:1162`, disconnect check at `:1195-1199`), `abort_submission` (`:1266`), `release_request` (`:1287`), `_retire` (`:651`). Data worker: `PreprocessWorker` (`mstar/api_server/data_worker.py:143`) with `new_request`, `abort_request`, `finished_reading` and `received_final_chunks` (`:247`, `:253`, `:264`, `:333`), `PreprocessWorkerThread.run` (`:1273`), output order `RequestOutputState` (`:427`) and `_queue_completed_output` (`:1012`). Rust frontend: `RustFrontendBridge._submit`, `_relay` and `_abort` (`mstar/api_server/rust_frontend.py:154`, `:197`, `:213`).
- **Keeps:** The engine sees only the key, so a client reusing its `request_id` cannot collide with an older submission still tearing down (`entrypoint.py:555-561`). One request's chunks reach the client in the order their reads started, whatever order the reads finish (`data_worker.py:427-443`). A completed request is released only when the data worker has received every chunk in `output_chunk_counts`, or after a 15 s TTL with an error (`entrypoint.py:415`, `:682-701`). Every handler exit that did not finish goes through `abort_submission`, then the data worker's ABORT_REQUEST, then the conductor's drain.
- **Used by:** `/generate` (`entrypoint.py:1866-1889`), `/generate/ws` (`:1658`), warmups (`:1403`), the OpenAI routes (`mstar/api_server/openai/serving_chat.py:26`, `:38`, `:88`, `mstar/api_server/openai/_util.py:32`), `RustFrontendBridge` (`rust_frontend.py:164-220`).
- **Extend via:** A new endpoint calls `submit_request`, then `iter_result_chunks` or `iter_result_chunk_batches` for streaming (abort on early exit is built in) or `collect_results(request_id, raw_request)` otherwise (disconnect checked every `DISCONNECT_CHECK_S`), and `release_request` when the results will not be read. The tempting duplicates are a handler polling `pending_requests` itself, its own disconnect watcher, or an ABORT_REQUEST sent to the conductor directly rather than through the data worker.
- **Breaks if:** Code keys on the client's `request_id` instead of the submission key, so a retry under the same id reads or aborts the wrong submission (`_bind` and `submission_key` at `entrypoint.py:962`, `:971` exist for this). The abort on a client that leaves a streaming route also rests on the ASGI server. Starlette 1.10 listens for the disconnect only below spec 2.4 (`starlette/responses.py:272-285`), and there anyio starts the body before it cancels, so the body's `finally` runs. uvicorn 0.28.0 reports 2.4 and raises from `send` on the response start, so the body never starts and nothing aborts it. 0.28.1 to 0.32.0 report 2.4 without raising, so a left stream runs until it ends or hits the 600 s `--timeout`. 0.32.1 is back on 2.3, but `pyproject.toml` puts no bound on uvicorn (#701 review, main `e7d0315e`). A handler that awaits a result before it returns its response has no Starlette listener during that wait: only `create_speech` does, for its first chunk (`serving_speech.py:125`), so a client that leaves then holds its pieces until the first result arrives. `_iter_result_chunk_batches` already wakes every 0.05 s for its timeout (`entrypoint.py:1283`), so that is where a disconnect check fits, not a second watcher in the handler (#476 review, main `55223944`).

- **Wakeups (main `437191f8`).** The data worker thread waits on its own communicator's poll with an `EventWakeup` registered (`PreprocessWorker.__init__`, `mstar/api_server/data_worker.py:225`; `_idle_wait` at `:1620`): every producer method signals it, and a finished tensor read or encode does too (`register_futures`, `:1187`). The API server's message thread does not wait on anything: it sleeps 1 ms after every pass (`entrypoint.py:1170`), so a frame waits up to one nap before it reaches the data worker and a chunk up to one more before its handler wakes. `_prune_recently_completed` runs at the top of a pass (`:962`), so a request is released on the pass after the one that drains it. A new producer for either loop signals its wakeup, or it is served by the nap or the idle backstop with nothing to say so. #939 (open) adds the outbound direction (`ResultQueue`, flushed per batch, polled by the message thread with a 1 ms backstop).

### Process CPU budget
- **Does:** Says how many CPUs a process can keep busy at once (its affinity, capped by the tightest cgroup v2 `cpu.max` quota), and the API server's pools are sized from it.
- **Where:** Checked at main `f7cb5ca9`. `cgroup_cpu_quota` and `usable_cpus` (`mstar/utils/cpus.py:17`, `:40`, from #903). Callers: the API server's intra-op pool through `default_preprocess_threads` (`mstar/api_server/entrypoint.py:2501`, used by `_set_preprocess_threads` at `:2539`), the data worker's encode pool through `encode_workers` (`mstar/api_server/data_worker.py:97`, pool at `:625`), and the PNG deflate threads `PNG_WORKERS = min(8, usable_cpus())` (`mstar/model/components/diffusion/image_io.py:84`).
- **Keeps:** A pool never runs more threads than the quota lets run, so a fork-join op doesn't wait on a parked thread. It reads the calling thread's mask, so it must run before any thread is pinned (today all callers run at startup or module import).
- **Used by:** The API server process only. Workers keep torch's default intra-op pool (one thread per CPU in the affinity).
- **Extend via:** A new pool or a thread-placement rule takes its count or its CPUs from this module. The tempting duplicate is a second module that reads `os.sched_getaffinity(0)` or `os.cpu_count()` on its own (#919's first `step_threads.py` and `cpu_list.py`), which then reserves CPUs the pools here still count. #919 (open, at `e58fb549`) folds its placement into this module as `CpuPlan`, built by `deployment_plan` in the API server from the config and in each worker from the conductor's device list.
- **Breaks if:** Called from a pinned thread (it returns 1), or a placement elsewhere reserves CPUs without taking them out of this count.
- **See also:** `lifecycle.md` › Media decode and model preprocessing in the data worker (the intra-op pool).
