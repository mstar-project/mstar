# Worker-side scheduling mechanisms on main

Checkout: main at `fa381afd6`. Paths are relative to the repo root. "Invariant N" means item N of the "Invariants" section of `AGENTS.md`.

## Stage order, for orientation

`Worker.run` (`mstar/worker/worker.py:4319`) loops at `worker.py:4519`. Each pass runs the admit fence (`:4531`), deferred removes, admit errors and drains (`:4533-4540`), messages and follower-stamped removes (`:4548-4550`), tensor readiness (`:4557`) and stream buffers (`:4564`). It then builds the next step with `_build_speculation` (`:4578`) and arms its pre-plan (`:4584`). With a step in flight, a TP follower waits in `_await_tp_follow_step` (`:4599`) and every other worker in `pending.future.result()` (`:4611`). After that come admit-refusal and failed-rid handling (`:4661-4685`), output threading and settle (`:4687-4706`), the speculative submit (`:4708-4749`), postprocess of N (`:4767-4772`) and a second teardown pass (`:4783-4794`). With no speculation the pass schedules fresh (`:4814-4822`) and submits (`:4849`). The thread-by-thread account is `.claude/skills/async-worker/SKILL.md` (Invariant 7).

### Request handles (RidTable)
- **Does:** Maps each wire request id to a small recycled integer that keys all worker-local request state.
- **Where:** `mstar/worker/rid_table.py:23` (`RidTable`), owned by `PythonGraphRuntime` (`mstar/graph/runtime/python.py:151`). Entry points are `intern` (`rid_table.py:31`, called at `python.py:221`), `release` (`rid_table.py:62`, called at `python.py:312`), and the worker's `_rid` and `_rid_str` (`worker.py:810`, `worker.py:815`).
- **Keeps:** A handle is recycled on release, so every handle-keyed map has to be purged first, which is why `_graph_runtime.remove_request` is the last call in `Worker._remove_request` (`worker.py:1023-1024`). `MicroScheduler.pending_tp_follow_count` is the one map keyed by wire string instead (`rid_table.py:17-19`).
- **Used by:** `Worker._remove_request` (`worker.py:930`), parking of messages for unknown rids in `_process_message_list` (`worker.py:1254-1271`), `MicroScheduler.tp_rids` (`mstar/worker/micro_scheduler.py:355`), `maybe_send_zmq_to_tp_followers` (`worker.py:1762`), `_fail_requests` (`worker.py:4208`), `_is_tearing_down` (`worker.py:2667`).
- **Extend via:** New per-request state keys on the handle, is purged in `Worker._remove_request` before the runtime call (or in `MicroScheduler.clear_rid`, `micro_scheduler.py:1322`, for scheduler state), and is added to the list in the module docstring (`rid_table.py:12-15`). The tempting duplicate is a side dict keyed by the wire string, which then needs its own purge path.
- **Breaks if:** A handle goes on the wire or into a log line meant to match across ranks, or new handle-keyed state is cleared at the top of a per-step routine instead of on release (Invariant 14).
- **See also:** `lifecycle.md` › Worker-local request handles.

### Ready scan and engine readiness
- **Does:** Finds runnable rows by taking graph-ready nodes from the runtime and then asking the engine whether each row's resources are ready.
- **Where:** `MicroScheduler._scan_ready` (`micro_scheduler.py:685`) and `_check_ready` (`micro_scheduler.py:1273`), over `GraphRuntime.get_ready_nodes` (`mstar/graph/runtime/base.py:778`) and `Engine.check_ready` (`mstar/engine/engine.py:2211`). The stop-at-first-match variant is `MicroScheduler.has_ready_excluding` (`micro_scheduler.py:1203`) over `GraphRuntime.has_ready_excluding` (`runtime/base.py:764`).
- **Keeps:** Only nodes in `parallel_leader_nodes` start a step (`micro_scheduler.py:697-698`), and a terminal readiness outcome fails the rid through `admit_errors` instead of being rescanned (`micro_scheduler.py:1283-1293`). `Engine.check_ready` reloads an offloaded row when `allow_reload` is true (`engine.py:2228-2232`), so a scan can move pages.
- **Used by:** `get_next_batch` (`micro_scheduler.py:653`, `:658`), `_park_other_walks` (`:678`), `_unready_backlog_rids` (`:925`), `pop_ready_rids` with `allow_reload=False` (`:478`), the fairness peek (`:1259-1271`) and through it `_build_speculation` (`worker.py:4265`). The worker reports terminal outcomes at the top of the next pass (`worker.py:4539`).
- **Extend via:** A new reason a row cannot run yet is a resource-level `check_ready` outcome, retryable or `terminal` (Invariant 1). The tempting duplicate is a second filter over the scan output in the worker or scheduler, which repeats a readiness check per waiting row per step (Invariant 6).
- **Breaks if:** A scan runs while the in-flight step's admit is outstanding, since its reload lands in a window the followers replay differently (Invariant 11), or a follower path asks with `allow_reload=True`.
- **Scan order:** The two runtimes yield ready rows in different orders. Python walks `per_request_queues` in insertion order, which is the order `add_request` ran for that worker graph (`mstar/worker/node_manager_utils.py:126-133`), so oldest request first. Rust walks `self.requests` by handle (`rust/src/graph/runtime.rs:488`), and both recycle handles LIFO (`rid_table.py:43`, `runtime.rs:53`). Neither is the order rows turned ready. Checked at 437191f8 for #955: at a capped loop both orders starve a request the same way, so the order decides only which request loses.
- **See also:** `graph-runtime.md` › Ready scan, pop and push back, `engine-resources.md` › Readiness, retrieve and publish.

### Do-not-start set (failed, pending remove, held)
- **Does:** Stops the scheduler starting new work for rows that failed, have a deferred remove, or are in OOM backoff.
- **Where:** `MicroScheduler.failed_rids` (`micro_scheduler.py:253`), `pending_removes` (`micro_scheduler.py:276`, the same dict as `Worker._pending_removes`, shared at `worker.py:657`) and `held_until` (`micro_scheduler.py:273`). Writers are `fail_rids` (`:1315`), `hold_requests` (`:349`, backoff `HOLD_BACKOFF_SECONDS` at `:213`) and `clear_rid` (`:1322`). Expiry runs at the top of `get_next_batch` (`:577-580`).
- **Keeps:** A row in the set is neither scanned nor asked for engine readiness, because asking would reload an offloaded row straight into another OOM (`micro_scheduler.py:883-886`). The exception is a TP-follow batch, which runs even with locally failed rids because rank 0 is already waiting in its collective (`micro_scheduler.py:582-589`).
- **Used by:** The predicate is restated in `_scan_ready` (`micro_scheduler.py:695`), `_live_backlog` (`:868-872`), `_unready_backlog_rids` (`:888-891`), `_backlog_has_schedulable` (`:1166-1169`), `has_ready_excluding` (`:1251-1255`), `pending_rows` (`:1301`), `Worker._is_tearing_down` (`worker.py:2665`) and `Worker._publishable_request_ids` (`worker.py:2420-2421`). Drains use `fail_rids` as their stop gate (`worker.py:1071-1074`), and `_fail_requests` filters out torn-down rids so the set never keeps one the conductor will not REMOVE (`worker.py:4202-4205`).
- **Extend via:** A new reason to stop starting work for a request goes into one of the three sets through `fail_rids` or `hold_requests`. The tempting duplicate is a fourth set, which would have to be added at every site above.
- **Breaks if:** The restated sites drift. They already differ: the runtime-scan half of `has_ready_excluding` excludes failed and held rids but not `pending_removes` (`micro_scheduler.py:1251-1255`), while `_scan_ready` excludes all three (`micro_scheduler.py:695`). Checked: the cost is performance only. A request whose remove is deferred while its step runs still counts as other ready work, so a speculation chain (or a TP follower's fairness check, `micro_scheduler.py:518-519`) yields once for a row `get_next_batch` then refuses. That is one lost overlapped step per deferred remove.

### Step selection order and round robin
- **Does:** Picks the next (node, walk) to run: the TP-follow FIFO head first, then backlogged keys oldest first, then the least recently scheduled ready key.
- **Where:** `MicroScheduler.get_next_batch` (`micro_scheduler.py:548`), with `_select_node_rr` (`:339`), `_mark_scheduled` (`:1038`), the cursor map `node_and_walk_to_last_batch_num` (`:271`) and `SchedulingType` (`:187`).
- **Keeps:** Every scheduled step advances the cursor, including steps served from the backlog (`_build_and_schedule`, `micro_scheduler.py:986`) and follower steps (`pop_ready_rids`, `:504-505`). A targeted call never takes from the TP-follow FIFO (`micro_scheduler.py:590`).
- **Used by:** The worker's non-speculative path (`worker.py:4817`, `worker.py:4822`), the yield-away build (`worker.py:4293`), the speculation fresh merge (`worker.py:2789`).
- **Extend via:** A new policy is a `SchedulingType` member handled in `get_next_batch`, which raises for anything but round robin (`micro_scheduler.py:599-600`). Priority is a recorded TODO for a model-declared (node, walk) priority (`micro_scheduler.py:189-193`). The tempting duplicate is ordering logic in the worker, for example in `_choose_spec_target`, whose own TODO points tie-breaking back at the micro-scheduler (`worker.py:2681-2682`).
- **Breaks if:** A new path schedules a batch without going through `_build_and_schedule`, so its walk reads as least recent for ever (`micro_scheduler.py:958-961`), or a cap-0 walk is picked and starves the walk that would free room (`micro_scheduler.py:659-663`).

### Backlog
- **Does:** Parks rows that were popped off their ready queues but did not fit in the step, and serves them before anything new.
- **Where:** `MicroScheduler.backlog` (`micro_scheduler.py:269`), written by `_backlog` (`:1014`), read by `_schedule_key` (`:742`) with `_unready_backlog_rids` (`:874`), pruned by `_drop_backlogged_rid` (`:1049`). Rows live in `ScheduledBatch` (`:43`) and move through `merge` (`:116`), `split_off_first` (`:130`) and `discard_rid` (`:95`).
- **Keeps:** A backlogged row is already off its ready queue and marked in flight (`micro_scheduler.py:1026-1029`), so the backlog is its only holder and parking must merge rather than replace (`:1017-1019`). Its readiness scan stops after one step's worth of rows (`micro_scheduler.py:899-909`).
- **Used by:** `get_next_batch` (`micro_scheduler.py:645-656`), `_build_and_schedule` (`:977-978`), `_park_other_walks` (`:683`), `room_for_continuing` (`:1177`), `backlog_splits_from` (`:842`), `has_ready_excluding` (`:1235`), `pending_rows` (`:1303`, read by `mstar/worker/worker_metrics.py:153`), `Worker._try_speculate_next` (`worker.py:2723-2725`).
- **Extend via:** Derived per-row facts go on `ScheduledBatch` (Invariant 6), rows leave only through `discard_rid`, and requests leave through `fail_rids` or `clear_rid`, which call `_drop_backlogged_rid`. The tempting duplicate is a worker-side queue of waiting rows, or pushing overflow back to the ready queues, which `FIFOBatchBuilder` does only on a step that served a backlog (`mstar/worker/batch_builder.py:137-143`).
- **Breaks if:** A row leaves the backlog without being scheduled, re-parked, or pushed back with its in-flight flag cleared, and the request hangs with no error.

### Batch builder
- **Does:** Decides, for one key's backlog and fresh rows, which rows run this step, which stay parked and which go back to their ready queues.
- **Where:** `BaseBatchBuilder` (`batch_builder.py:82`) with `build_batch` (`:84`), `room_for_continuing` (`:87`) and `chain_must_yield` (`:102`). The only implementation is `FIFOBatchBuilder` (`:115`). Its input and output are `BatchBuildRequest` (`:20`) and `BatchBuildResult` (`:45`). The single call site is `MicroScheduler._build_and_schedule` (`micro_scheduler.py:952`).
- **Keeps:** Every row handed in comes back in exactly one of `scheduled`, `backlog` or `returned`, which `_refuse_lost_rows` asserts (`micro_scheduler.py:991`). Speculation sizes and ends its chain with the same builder's `room_for_continuing` and `chain_must_yield`, so the chain and the next build agree on what fits.
- **Used by:** `_build_and_schedule` (`micro_scheduler.py:973`), `room_for_continuing` (`:1185`, `:1191`), `backlog_splits_from` (`:845`).
- **Extend via:** A new composition rule is a `BaseBatchBuilder` subclass registered in `BatchBuilderType` and `make_batch_builder` (`batch_builder.py:245`, `:249`), overriding the two speculation hooks when it changes what a merge takes. `Worker` builds the scheduler without `batch_builder_type` (`worker.py:603-608`), so a new builder also needs a config path. The tempting duplicates are row filtering in the speculation path or in model code (Invariant 1). `can_batch` is not a selection hook, since the engine reads it after selection to choose a batched or per-row forward (`engine.py:974`, `engine.py:1015`).
- **Breaks if:** The builder drops or invents rows, or its speculation hooks disagree with `build_batch`.

### Batch caps
- **Does:** Bounds the rows in one step for each (node, walk), and per real walk inside a mixed step.
- **Where:** `MicroScheduler._max_batch_size` (`micro_scheduler.py:1092`) over `Engine.get_max_batch_size` (`engine.py:2192`), and `_walk_row_caps` (`micro_scheduler.py:1078`) over `Engine.get_max_rows_in_combined` (`engine.py:2188`). ### In-flight flag
- **Does:** Marks a (rid, node) as claimed by a running, speculated or backlogged batch so that an arriving input does not queue it a second time.
- **Where:** `GraphNode._in_flight` (`mstar/graph/base.py:247`), checked in `register_ingested_input` (`graph/base.py:805-826`) and set through `GraphRuntime.set_in_flight` (`runtime/base.py:601`). - **Keeps:** While the flag is set an arriving input does not put the node back on a ready queue, and the flag has to survive node completion until the speculation resolves (`graph/base.py:807-826`, `runtime/base.py:613-618`). It is separate from `Worker._in_flight_rids` (`worker.py:638`), which gates teardown and is reset by `_set_pending` (`worker.py:4459-4462`).
- **Used by:** The fresh submit (`worker.py:4847`), the clear after N (`worker.py:4620`, `:4668`), backlog park and return (`micro_scheduler.py:1029`, `:980`), the speculation settle (`worker.py:2622-2628`), the error path (`worker.py:4136`, `:4152`, `:4179`).
- **Extend via:** A new path that holds popped rows sets the flag through these calls and clears it alongside `push_back_node` when it gives the rows back. The tempting duplicate is a worker-side set of rows already scheduled.
- **Breaks if:** Rows are popped and then dropped with neither a run nor a clear plus push-back, so their nodes never become ready again.
- **See also:** `graph-runtime.md` › In-flight flag.

### Admit refusal and OOM eviction
- **Does:** Re-queues a step whose admit refused it, and on allocation failure offloads one least-recently-used request or holds rows so the retry is smaller.
- **Where:** `Worker._handle_admit_failure` (`worker.py:2254`), `_handle_allocation_failure` (`:2321`), `_handle_unservable` (`:2292`), `_try_offload_cold_request` (`:1488`), `_select_eviction_victim` (`:1545`), `EvictionPolicy` (`:297`), with LRU stamps in `_last_active` (`:626`).
- **Keeps:** Every retryable refusal pushes the whole batch back (`worker.py:2285`, `:2351`), and only rank 0 evicts or holds while a follower returns after the push-back and receives rank 0's choice as a resident delta (`worker.py:2340-2346`, `:2365-2366`).
- **Used by:** The main loop on `admit_error` (`worker.py:4661-4674`). LRU stamps are written at `worker.py:838` and `:3303` and purged at `:1019-1020`. The postprocess write stamps `(rid, node)` for every node that ran, but the purge covers only `evictable_nodes()`, so entries for other nodes outlive the handle (harmless today, eviction reads only evictable nodes; checked at b1e3430d). A scheduler order that serves the least recently run row first (#955's turns) makes the LRU victim outside the step the next row in line. Holds go into the do-not-start set through `hold_requests` (`worker.py:2377`, `:2391`).
- **Extend via:** A new victim rule is an `EvictionPolicy` member dispatched in `_select_eviction_victim` (TODO at `worker.py:300-303`), and a new refusal kind is an `AdmitFailedReason` with `terminal` set to match. The tempting duplicate is a retry or backoff loop inside a resource or the engine, which turns schedulable backpressure into a failure (Invariant 1).
- **Breaks if:** A follower evicts or holds on its own, or the eviction decision reads state the other ranks cannot derive (Invariant 11).
- **See also:** `engine-resources.md` › Eviction, offload and the TP resident journal, `lockstep.md` › 9. Resident-set journal.

### Teardown ordering: admit fence, deferred removes, drains
- **Does:** Orders every teardown and page move against the in-flight step, so nothing is freed under the GPU thread and followers repeat rank 0's order.
- **Where:** `Worker._await_admit_settled` (`worker.py:2217`), `_remove_request` (`:929`), `_apply_pending_removes_safe_to_drop` (`:4054`), `_removes_awaiting_step` with `_removal_step_reached` and `_apply_removes_whose_step_landed` (`:643`, `:4033`, `:4041`), and the two-phase drain `_drain_request`, `_begin_drain`, `_complete_drain_if_ready`, `_apply_pending_drains` (`:1026`, `:1045`, `:1078`, `:1108`). Scheduler cleanup is `clear_rid` and `clear_wire_rid` (`micro_scheduler.py:1322`, `:1333`).
- **Keeps:** Nothing that moves pages runs until the in-flight step has admitted (`worker.py:4527-4531`), and a remove or drain for a rid in `_in_flight_rids` is deferred (`worker.py:972-974`, `:1039-1041`). A follower applies only rank 0's forwarded teardowns, after the step they were stamped with and in rank 0's order (`worker.py:941-958`, `:966-971`, `:4063-4064`).
- **Used by:** The main loop top (`worker.py:4531-4540`), after messages (`:4550`), after postprocess (`:4783-4785`), the idle follower (`:4788-4794`), the OOM path (`:2356`, `:2363`), message dispatch (`:1275-1277`). READS_DONE also waits for in-flight reads and queued TP-follow batches (`worker.py:1088-1096`).
- **Extend via:** New per-request cleanup goes inside `_remove_request` before the final runtime call, and a new holder of rids extends `_in_flight_rids`, as `_try_follow_speculation` does (`worker.py:3065`). The tempting duplicate is a new deferral set, or cleanup placed at a different loop stage.
- **Breaks if:** A mutation of replicated state lands between a step's broadcast and its admit (Invariant 11), or a follower tears down out of rank 0's order.
- **See also:** `lockstep.md` › 12. Admit fence, `lockstep.md` › 13. Stamped teardown ordering, `lifecycle.md` › Two-phase teardown barrier, `lifecycle.md` › Worker removal sequencing.

### TP lockstep follow
- **Does:** Makes followers run exactly the steps rank 0 broadcasts, either serially from a FIFO or by rebuilding rank 0's speculative head during their own step N.
- **Where:** The leader sends with `maybe_send_zmq_to_tp_followers` (`worker.py:1723`) and `_broadcast_tp_nospec` (`:1776`). The FIFO is `tp_batches_pending_schedule` (`micro_scheduler.py:260`) with `register_tp_follow` (`:364`), `peek_tp_follow` (`:376`), `settle_tp_follow_delta` (`:400`), `pop_tp_follow_head` (`:427`), `pop_ready_rids` (`:442`), `_try_schedule_tp_follow` (`:508`) and `tp_rids` with `REMOVED_RID` (`:355`, `:31`). The async follower is `_await_tp_follow_step` (`worker.py:3128`), `_try_follow_speculation` (`:2925`), `_close_tp_follow_step` (`:3108`), `_step_voids_head` (`:3119`) and `_tp_nospec` (`:586`).
- **Keeps:** A follower pops the leader's rid set all or none, only after replaying the head's resident delta and prefix decisions, and `pop_tp_follow_head` is the only exit from the FIFO (`micro_scheduler.py:400-449`). Under TP async the leader sends exactly one head or one marker per step, and the follower settles it before postprocessing N (`worker.py:2498-2505`, `:3131-3133`).
- **Used by:** `get_next_batch` (`micro_scheduler.py:590`), message dispatch (`worker.py:1286-1289`), the main loop (`worker.py:4280-4285`, `:4314`, `:4593-4601`, `:4840`), the drain ACK (`worker.py:1095`), removal ordering through `last_consumed_tp_seq` (`micro_scheduler.py:333`). The TP async flag is checked for agreement across ranks at startup (`worker.py:2469`, called at `:4348`).
- **Extend via:** A decision the followers cannot derive rides on `ScheduleTPNode`, filled in `maybe_send_zmq_to_tp_followers` and replayed in `settle_tp_follow_delta`, the way `resident_delta`, `prefix_hits` and `page_trails` are. The tempting duplicate is a separate per-step message or a follower-local choice. `max_consec_tp_follower_batches` exists (`micro_scheduler.py:219`) but `Worker` leaves it at its default of 1 (`worker.py:603-608`).
- **Breaks if:** A follower branch reads per-rank state, or a new `ScheduleTPNode` field has no wire encoder (Invariants 11 and 6). TP async is off by default (Invariant 7), so a change to that path is exercised only with `MSTAR_TP_ASYNC_SCHED` set.
- **See also:** `lockstep.md` › 6. ScheduleTPNode broadcast, `lockstep.md` › 7. Follower FIFO and serial follow path, `lockstep.md` › 8. Follower settle seam, `lockstep.md` › 14. TP async scheduling protocol.

### Speculation chain
- **Does:** Builds step N+1 while N runs, as N's continuing rows plus fresh rows of the same target, or as a yield-away batch from the scheduler.
- **Where:** `Worker._build_speculation` (`worker.py:4224`), with `_can_speculate` (`:2433`), `_choose_spec_target` (`:2670`), `_try_speculate_next` (`:2686`), `_assemble_speculation` (`:2518`), `_thread_outputs_to_speculative` (`:2846`), `_settle_speculation` (`:2594`), `Speculation` (`:260`) and `_SpecFairness` (`:233`). The runtime side is `speculate_node`, `prep_spec_rids` and `commit_speculation` (`runtime/base.py:803`, `:817`, `:857`).
- **Keeps:** Target eligibility lives in the runtime's `speculate_node`, which checks `enable_async_scheduling` at both ends and admits a parallel node only as a same-node loop-back on the TP async leader (`python.py:691-716`). A speculation settles exactly once (`worker.py:2641-2642`), and on abandon only its fresh rids are pushed back because N's routing re-readies the continuing ones (`worker.py:4646-4658`, `:4180-4189`).
- **Used by:** The main loop (`worker.py:4578`, `:4623-4659`, `:4687-4749`), the error handler (`worker.py:4153-4189`). The chain yields on `MSTAR_MAX_CONSECUTIVE_SPEC_STEPS` or when the peek finds other work (`worker.py:4262-4267`), and when the backlog holds another capture group (`worker.py:2723`).
- **Extend via:** A node opts out with `enable_async_scheduling=False` (`mstar/graph/base.py:240`). Eligibility changes go in `speculate_node` on both runtimes (Invariant 5), and the Rust side's filter is `AsyncEnabledChecker::can_speculate` (`rust/src/graph/runtime.rs:123`, see lockstep.md › Findings). New per-speculation state goes on `Speculation` and is released in `_settle_speculation`, and fresh rows come through `get_next_batch(target=..., pre_existing_batch_size=..., capture_group_of=...)` (`worker.py:2789-2794`). The tempting duplicates are a worker-side target filter and a second rollback path.
- **Breaks if:** A new abandon path skips the fresh-rid push-back, or returns a stream chunk to its `StreamBuffer` before the undo takes it out of the node slot (`worker.py:2601-2606`). Output threading must not read tensor values (`worker.py:2852-2855`).
- **See also:** `graph-runtime.md` › Speculation targets and staged prep.

### Pre-plan on the plan thread
- **Does:** Reserves a replay slot and plans step N+1's resources on a separate thread while N's kernels run.
- **Where:** `_arm_speculation` (`worker.py:4449`), `_preplan_spec` (`:1941`), `_plans_ahead` (`:2444`), `_reset_skip_plan_flags` (`:1990`) and the GPU thread's wait and staleness check (`:2125-2149`). The engine API is `can_pre_plan`, `reserve_replay_slot`, `pre_plan_for_batch`, `preplan_is_stale` and `reset_pre_plan_for_batch` (`engine.py:2282`, `:2239`, `:2295`, `:2392`, `:2399`). The switch is `MSTAR_PRE_PLAN_SPEC` (`worker.py:4420`).
- **Keeps:** The plan thread waits only on N's `commit_done` (`worker.py:1968-1969`), and the GPU thread owns the plan future once the step is submitted (`:4725-4728`). Every path that drops a pre-planned speculation awaits the future before resetting its stage (`worker.py:4636-4641`, `:4750-4759`, `:4160-4172`, `:2142-2144`).
- **Used by:** The main loop (`worker.py:4584`), the async follower through the `arm` callback (`worker.py:3158`), the GPU thread (`worker.py:2125-2149`). A TP leader with the prefix cache open skips pre-plan for a yield-away step (`worker.py:2444-2449`).
- **Extend via:** A resource takes part through the engine pre-plan API and sets `force_double_buffer` when it does H2D into fixed buffers (Invariant 7). The tempting duplicate is planning in the worker or on another thread, which only adds GIL contention (Invariant 7).
- **Breaks if:** A stage is reset while its plan future still runs, or a dropped speculation's stage is left in place, so the next step to lease that slot promotes a stale plan (`worker.py:1993-1996`).
- **See also:** `engine-resources.md` › Pre-planning and slot double-buffering.

## Notes for reviewers

- The do-not-start predicate is written out at eight sites, and one already differs (see that block). A PR that adds a new exclusion reason or edits one site deserves a check of all eight.
- `MicroScheduler.__init__` accepts `max_consec_tp_follower_batches` and `batch_builder_type` (`micro_scheduler.py:219-220`), but `Worker` passes neither (`worker.py:603-608`). Production therefore runs `FIFOBatchBuilder` and a follower fairness cap of 1.
- Two open TODOs already say where a new ordering policy belongs: priority in `SchedulingType` (`micro_scheduler.py:189-193`) and target tie-breaking in the micro-scheduler (`worker.py:2681-2682`).
- `disable_spec_node_walks`, the startup-time speculation filter described under "Design patterns" in `AGENTS.md`, lands with #365 (about to merge). Until then nothing under `mstar/` references it. #365 also moves the `_unready_backlog_rids` copy of the do-not-start check into `_waiting_rids`.
