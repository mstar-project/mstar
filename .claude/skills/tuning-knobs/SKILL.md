# Tuning knobs by symptom

Most of M*'s performance switches are per deployment (`knobs:` and other keys in the serving config, each with an `MSTAR_*` override) or per capture config, so a model can often be fixed without code. This page maps a symptom you can measure to the switch that addresses it. It is not a list of every knob: [docs/environment_variables.rst](../../../docs/environment_variables.rst) is the reference for defaults and exact meaning, and [docs/serving.rst](../../../docs/serving.rst) for the config keys.

Rules that apply to every entry:

- **Confirm the symptom first, with the harness named in the entry.** [The benchmarking skill](../benchmarking/SKILL.md) says how to tell CPU- from GPU-bound; most of these switches help only one of the two.
- **A/B on one tree, fresh boots alternated, at several concurrencies, and on the workloads you didn't target** (invariant 10). An env override (`MSTAR_*`) is the cleanest arm switch: it needs no edit between boots.
- **Give a competitor the same host settings.** A clock floor that M* sets for itself (`uclamp_min`) is worth as much to vLLM or SGLang: on Cosmos3-Edge it gave vLLM +48% at c=64. Launch the competitor under the same `util_min` (set with `sched_setattr` before exec, so its threads and subprocesses inherit it) and check its threads' values after boot.
- **Prefer a per-node or per-config setting over a process-wide one** (invariant 4). Several of these are process-wide; the entry says so.
- **Don't judge batching from fixed-length closed-loop runs alone.** With `ignore_eos` and one output length, a round's requests finish together and their replacements arrive together, so every round boundary is a burst of prefills. That exaggerates decode fragmentation and penalizes anything that lengthens TTFT. Rerun with varied lengths and staggered starts (`benchmark/` clients or your own) before deciding. A useful check: if every request past its prefill rides every decode step, rows per decode step ≈ concurrency × 255 · ITL / (TTFT + 255 · ITL) for 256-token replies; a match means decode batches aren't splitting, and the shortfall is requests not yet decoding.

## Host-bound

| Symptom (how to confirm) | Switch | Notes |
| --- | --- | --- |
| Host-bound numbers that move with the host's load, threads sampled near the lowest clock (`/proc/<pid>/task/*/stat` CPU and `scaling_cur_freq`), a `schedutil` governor | `knobs: uclamp_min: 1024` (#1266; `MSTAR_UCLAMP_MIN`) | Asks the kernel for a clock floor for the worker and API server. Cosmos3-Edge reasoner, live toggle on one server: c=32 1223 → 1847 tok/s. Does nothing under a governor that doesn't read utilization. |
| GPU idle just before each decode replay, with the launch arriving after the GPU went idle (nsys `-t cuda`: kernel start vs `cudaGraphLaunch`), and `worker.gpu_thread.total` about as long as the decode graph | `knobs: step_threads: serial` (#1249; `MSTAR_STEP_THREADS`) | Runs a step's host work on the main thread: no handoffs for the governor to clock down. Cosmos3-Edge: decode step GPU time 2.5 → 2.23 ms (the graph's own), iteration −25%, +5–13% tok/s on a jittered client. Lengthened TTFT at c=32 (71 → ~100 ms); per config. |
| `worker.gpu_thread.await_plan` a sizeable share of the step, `worker.plan_thread.pre_plan` near a millisecond (KV, attention, positions, sampler plans) | Resident planning: the submodule names `resident_walks()`, `knobs: resident_planning` stays `auto` | The worker log says why a node that names walks stays on the host (`resident planning stays off on <node>: …`). A resource shared with another node is refused on `main`; see the open PR on #1143. Cosmos3-Edge: `await_plan` 0.30–0.43 → 0.10–0.17 ms per step. |
| Pre-plan thread costing more than it overlaps on a shallow model (plan thread and GPU thread contending for the GIL; worse `iter_total` with it than without) | `knobs: pre_plan: false` | Measured +11% RTFx at c=1 and +6% at c=32 on Whisper Turbo (see `configs/whisper_large_v3_turbo.yaml`). Deep models want it on. |
| A collection almost every step at large decode batches (`gc.gen0` / `gc.gen1` spans in the phase table) | `knobs: gc_gen0_threshold` | At 128 rows a step keeps more than CPython's 700 young objects alive. |
| Deep C-state wake-ups between the step's threads (a held clock still loses to pinning) | `knobs: idle_hold: qos`, `knobs: step_thread_core` | Host-dependent; `/dev/cpu_dma_latency` is absent in many containers. Pinning was rejected as a general fix on shared hosts. |

## API server

| Symptom (how to confirm) | Switch | Notes |
| --- | --- | --- |
| TTFT that grows with concurrency while the worker's part stays flat: in `--log-stats-file` (per-request timelines), `recv → preprocess done` climbs under a burst (p95 ≈ concurrency × the c=1 value) while `conductor ingest → first chunk` doesn't | `PREPROCESS_PARALLEL = True` on the model; `preprocess_workers` in the serving config sizes the pool | Off by default: the data worker prepares one request at a time. Declare it only after checking the model's loaders and `process_prompt` keep no shared state, and that the work releases the GIL (media decode and torch ops do). Cosmos3-Edge reasoner, c=64 image burst: `recv → preprocess done` p50 60 / p95 945 ms against 40 / 60 ms worker-side; offline, 8 threads took a request from 10 to 2.3 ms (8 ms of it PNG decode). On, fresh boots alternated (fixed 256-token replies): c=32 7032 → 8380 tok/s, c=64 7412 → 9363, c=64 TTFT p50 1.34 s → 0.52 s; varied lengths +3% / +7%; c=1 TTFT +2.5 ms. |
| At high concurrency the API server falls behind both ways: `recv → preprocess done` and `conductor done → last chunk` (per-request timelines) grow with concurrency while the worker's part stays flat, and the API server process runs about a core of Python across its threads (`/proc/<pid>/task/*/stat`) | The Rust frontend: `mstar serve ... --rust-frontend` (build `mstar-server` with `cargo build --release --manifest-path rust/server/Cargo.toml`) | Serves HTTP, OpenAI translation and SSE from Rust; preprocessing stays in Python. Its output path costs ~8 µs of API-server CPU a streamed token against 18 µs (`benchmark/api_output_path`). Cosmos3-Edge reasoner, with `PREPROCESS_PARALLEL` already on: c=64 +32% (fixed 256-token replies), +15% with varied lengths, TTFT p50 0.38 → 0.07 s; c=32 +8%. Check the model's routes are ported (`NOT_PORTED` in `test/rust/test_rust_openai_adapters.py`). |

## GPU-bound

| Symptom (how to confirm) | Switch | Notes |
| --- | --- | --- |
| Decode GEMMs slower in the graph than cuBLAS (nsys: `triton_tem_*` kernels where a competitor runs `nvjet`), or decode speed that differs between boots of the same code | Capture config `inductor_options={"max_autotune_gemm_backends": "ATEN"}` (#1287), or `compile_mode` / `-O1` | Max-autotune's timings of decode-width GEMMs were bimodal across processes on one H200 (cuBLAS ranked first in 6 of 18 runs, outside the top 10 in the rest), and the slow mode picked templates ~2x slower in the graph. Read Inductor's own tables with `TORCHINDUCTOR_MAX_AUTOTUNE_REPORT_CHOICES_STATS=1` and a fresh Inductor cache. Pinning prefill GEMMs measured neutral on Cosmos3. |
| Decode capped below the concurrency (rows per step stop at a ladder rung) | `MSTAR_DECODE_BUCKETS` (`SampledTokenDecoder` models) | The largest bucket is also the scheduler's cap on rows per decode step. |
| Decode steps padded far past their rows (nsys: the 64-row graph launched far more often than rows per step would need, a competitor with rungs between the powers of two) | Add rungs to the model's `DECODE_CAPTURE_BATCH_SIZES` (`MSTAR_DECODE_BUCKETS` to A/B) | Cosmos3-Edge reasoner, 1..64 -> +24, +48: +7% at c=32, +14% at c=64. Each rung is one more capture at startup. |
| A ragged attention (ViT) whose head dim FlashInfer doesn't have (not 64/128/256): `F.pad` / `constant_pad_nd` and a slice-copy around every attention call in the trace | `resources: <key>: backend: dense` in the serving config, or `backend=RaggedAttnBackend.DENSE` on the spec: FA3 varlen, unpadded | Check FA3 imports: `_fa3_unavailable_reason()` in `mstar/engine/resources/attn/dense.py`. A wheel built for another CUDA (fa3-fwd 0.0.3 is CUDA 13) fails to import, and DENSE silently runs on FlashInfer. Cosmos3-Edge vision: largest replay 22.5 -> 18.9 ms. |
| A bf16 encoder's trace full of `direct_copy` / `bfloat16_copy` kernels and `layer_norm<float, float>` around each norm | `disable_autocast = True` on the submodule (plus `BLOCK_LOOP_DTYPE` on a `PackedBlockLoopEncoder`) | Autocast runs LayerNorm in fp32 and casts its output back once per projection reading it. Cosmos3-Edge vision: 18.9 -> 14.9 ms a replay, same rounding. Only for a node whose weights are already in the target dtype. |

## Prompts stalling decode

| Symptom (how to confirm) | Switch | Notes |
| --- | --- | --- |
| Standalone prefill steps interleaved with decode (phase table: `step.<node>.prefill*` counts beside `decode`), each stopping every decode stream | A combined walk (`get_combined_graph_walks`, mixed steps), and for media prompts `SampledTokenDecoder.MIXED_MEDIA` (open PR) | Cosmos3-Edge with media rows in mixed steps: standalone image prefills 155–342 → 11–92 per window. |
| Yield-away steps (`worker.schedule_yield_away` count) a large share of iterations although prompts could ride decode steps | `speculation_mixes_walks: {<node>: true}` (serving config) | On, a decode speculation chain merges the other walks of its combined walk instead of yielding to them. Defaults on only where the combined walk has a token budget (`max_batch_tokens`); without one a merged prompt runs whole and stretches the decode step it joins. |
| Speculation chains broken too often or not enough | `MSTAR_MAX_CONSECUTIVE_SPEC_STEPS`, `MSTAR_SPEC_PEEK_FOR_FAIRNESS` | Process-wide; see the async-worker skill before touching them. |

## Measured neutral, so not switches to reach for

Compiling a captured ViT's blocks when its time is head-dim padding (Cosmos3-Edge: 814 → 436 kernels, 7% off the graph, nothing end to end; the pads to FlashInfer's 128 were ~39% of the graph). Pinning prefill GEMMs to cuBLAS (Cosmos3-Edge). `speculation_mixes_walks` on a combined walk without a token budget (Cosmos3-Edge reasoner with media rows in mixed steps: every prefill merged and yield-aways fell 20-27%, but the merged steps ran 45% longer and throughput was level to 7% lower). Running a ViT on a second worker of the same GPU under MPS (`mps: true`, Cosmos3-Edge: level at c=64, worse at c=32). A finer (1.5x) patch-bucket ladder for a block-loop encoder (Cosmos3-Edge: vision steps 15% shorter, end to end level to worse). Running a block-loop encoder eagerly at exact sizes to avoid bucket padding (Cosmos3-Edge: ~15 ms of host a vision step launching ~650 kernels against ~1.3 ms for a replay; −7% at c=64, −17% with varied lengths). More prompt rows per mixed step than `MIXED_MAX_PREFILL_ROWS` = 4 when prompts reach the worker slowly (Cosmos3-Edge, Python frontend: 8 and 16 level). Neutral switches get removed rather than left behind a flag (invariant 9), so add a line here instead of keeping the code.
